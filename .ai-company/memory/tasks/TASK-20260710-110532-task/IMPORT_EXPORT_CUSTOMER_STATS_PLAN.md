# 店铺创建者专用工单详情导入导出计划书

Task: `TASK-20260710-110532-task`

Status: owner-requested revised plan

Owner: Hexiang Huang / 鹤祥

Prepared: 2026-07-10

Scope: 计划与验收合同；本文件不代表已经实施、迁移或上线

## 1. 最终目标

在 `设置` 中建设一个只对当前店铺主店主开放的“工单数据”区域，提供四项能力：

1. `导出工单详情`：导出当前活动店铺的工单完整当前资料，供外部整理。
2. `下载空白模板`：单独下载只有字段、说明和可选值、没有任何真实店铺数据的模板。
3. `导入工单数据`：把 RepairDesk 导出文件、空白模板整理后的文件或 SeaTable 旧数据导回系统。
4. `导出客户统计`：单独导出当前活动店铺的客户经营统计；该文件不作为工单导入模板。

硬性结果：

- 订单页面不再显示“导出当前页/导出选中”或导入按钮。
- 所有入口只放在 `设置 > 工单数据`。
- 只有当前店铺的主店主账号可以看到和使用这些能力。
- 经理、技师、前台、查看者、平台管理员和普通支持账号都不能导出或导入。
- 每次只处理当前活动店铺，不能跨店铺合并导出或导入。
- 导入永远不清库，不因文件少行、删行或空白单元格删除已有资料。
- 导出的已有工单可以整理后导回，并按明确匹配规则更新允许修改的字段。

## 2. 当前项目事实与计划修正

已核对的当前实现：

- 设置页目前没有工单数据导入导出 section。
- 订单列表当前有浏览器端 `导出当前页/导出选中`，只导出当前已经加载的列表字段，不是完整工单详情，也没有服务端导出权限校验和完整审计。
- 当前权限矩阵允许 `owner` 和 `manager` 使用 `order:export` / `customer:export`；这与老板最新要求不一致，实施时必须把经理改为拒绝。
- `stores.owner_user_id` 已存在；创建店铺时会写入创建账号 ID，因此可以可靠区分“主店主账号”和普通 `owner` 角色成员。
- 当前工单读取已经以服务端 `actor.storeId` 过滤 `repair_orders.store_id`，新导出/导入必须沿用并加强这个边界。
- 当前 SeaTable parser 可以复用字段识别；现有 CLI apply 会执行 `CLEAR_REPAIRDESK` 清理后再写入，绝不能接入设置页或新 API。
- 当前工单详情包含工单当前状态、客户、设备、供应商、维修项目、金额、事件、消息和附件；并非所有详情都适合回写。

本次计划对原计划的主要修正：

- 权限从“owner/manager 可导出”收紧为“仅 `stores.owner_user_id` 对应的主店主账号”。
- 设置页成为唯一入口，订单列表原导出入口必须删除。
- 导出对象明确为“工单详情当前数据”，不是当前页面列表数据。
- 空白模板必须作为独立文件提供，不能用真实导出文件冒充模板。
- 导入、导出、模板和统计全部按当前活动店铺与当前账号双重隔离。

## 2.1 架构方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| A. 保留订单页客户端 CSV | 改动最小 | 只覆盖当前页、数据字段不完整、权限和审计不可靠、存在第二出口 | 拒绝 |
| B. 设置页服务端单 CSV | 权限和租户隔离可落地、实现较快 | 多维修项目、说明、历史和统计难以无损表达 | 仅作为兼容格式 |
| C. 设置页服务端 XLSX 工作簿 + CSV 兼容 | 能完整表达主表、维修项目、说明、历史和统计；适合外部整理后导回 | 需要受控引入 XLSX 依赖并增加解析安全审查 | 推荐 |

目标数据流：

1. 设置页请求服务端 capability。
2. 服务端验证登录账号、活动店铺、有效 owner membership 和 `stores.owner_user_id`。
3. 导出服务只读取 `actor.storeId` 下的数据并流式返回文件。
4. 导入 preview 把文件解析为绑定账号/店铺/file hash 的批次，不写业务数据。
5. Apply 重新校验同一批次、权限和版本，再调用现有工单业务服务逐行写入。

关键质量属性：默认拒绝、租户隔离、幂等、字段级可追踪、无清库路径、可处理部分失败、文件不公开缓存、批次可审计和可恢复。

实施批准后应建立 ADR 候选：`Settings-only primary-owner order data roundtrip`，记录为什么拒绝客户端 CSV、为什么选择服务端 XLSX + CSV 兼容，以及正式 owner 转让后的权限语义。该 ADR 在本计划阶段仅为 proposed，不能标记 approved。

## 3. 主店主身份定义与权限矩阵

### 3.1 主店主定义

允许操作的账号必须同时满足：

1. 已登录，且不是 system actor。
2. 当前活动店铺有效且状态允许业务操作。
3. 当前账号在该店铺有有效 `owner` 成员身份。
4. `actor.id === stores.owner_user_id`。

仅有 `owner` 角色但不是 `stores.owner_user_id` 的账号也必须拒绝。

店铺创建时，创建账号写入 `stores.owner_user_id`。如果以后执行正式店铺所有权转让，导入导出权应随新的 `owner_user_id` 转移，原创建账号立即失去权限；不能把离店的历史创建者永久保留为数据出口。

### 3.2 操作权限

| 操作 | 主店主账号 | 其他 owner 成员 | manager | technician | sales/前台 | viewer | platform/support |
|---|---:|---:|---:|---:|---:|---:|---:|
| 看见“工单数据”设置项 | Y | N | N | N | N | N | N |
| 下载空白模板 | Y | N | N | N | N | N | N |
| 导出工单详情 | Y | N | N | N | N | N | N |
| 导出客户统计 | Y | N | N | N | N | N | N |
| 上传文件并预览 | Y | N | N | N | N | N | N |
| 应用新增/更新 | Y | N | N | N | N | N | N |
| 强制处理版本冲突 | Y，逐行确认 | N | N | N | N | N | N |

权限不能只靠隐藏按钮。每一个模板、导出、预览和 apply API 都必须在服务端重新查询当前店铺并执行主店主断言；直接请求接口时也必须返回 `403`。

### 3.3 设置页显示规则

- Store Context 服务端返回布尔能力，例如 `canManageOrderData`，前端不自己猜 `owner_user_id`。
- 非主店主不显示“工单数据”导航项。
- 非主店主手动访问 `?section=order-data` 时，回到默认设置项并显示无权访问提示；不能渲染后再隐藏敏感数据。
- 平台管理员即使有平台权限或临时 support access，也不能获得批量导入导出能力。

### 3.4 轻量威胁模型

| 项目 | 内容 |
|---|---|
| 受保护资产 | 客户姓名/电话、设备标识、工单历史、金额、供应商、经营统计 |
| 潜在滥用者 | 普通员工、另一店铺账号、仅有 owner 角色但非主店主的成员、平台/support 账号、拿到旧文件的人 |
| 入口 | 设置页、直接 API、导出下载、XLSX/CSV 上传、preview batch、apply |
| 主要风险 | 越权批量导出、跨店读取/覆盖、恶意表格资源耗尽、旧批次重放、日志或下载链接泄露 PII |
| 最坏影响 | 整店客户数据泄露、另一租户工单被覆盖、付款/状态错误、无法追溯批量修改 |
| 核心控制 | 主店主双重断言、服务端 tenant guard、短期批次绑定、字段白名单、版本冲突、文件限制、私有下载、最小化审计 |

## 4. 设置页信息架构

唯一入口：`设置 > 工单数据`

页面分为四个不嵌套的功能区：

### A. 导出工单详情

- 日期范围：全部、今年、最近 12 个月、自定义。
- 工单状态、技师、付款状态、供应商筛选。
- 导出前显示预计工单数量和所属店铺。
- 主按钮：`导出工单详情`。
- 默认一次只导出当前活动店铺，不能选择“所有店铺”。

### B. 下载空白模板

- `RepairDesk 工单导入模板.xlsx`：推荐长期使用。
- `SeaTable RIPARAZIONE 兼容模板.csv`：用于旧表格整理。
- 主按钮：`下载空白模板`。
- 模板没有客户、电话、工单或任何真实业务数据。

### C. 导入工单数据

- 上传 `.xlsx` 或 `.csv`。
- 识别来源：RepairDesk 导出、RepairDesk 空白模板、SeaTable 兼容表。
- 选择模式：`只新增`、`只更新`、`新增并更新`。
- 固定顺序：上传 -> 校验 -> 预览 -> 逐项确认 -> 应用。
- 应用前明确显示所属店铺、操作者和影响数量。

### D. 导出客户统计

- 导出当前店铺客户统计，不合并其他店铺。
- 主按钮：`导出客户统计`。
- 统计文件只读，不通过工单导入入口回写。

### 4.1 订单页处理

- 删除订单列表中的 `导出当前页/导出选中` 按钮和客户端 Blob 导出逻辑。
- 订单页保留筛选、打印、新建和业务操作，不放置导入导出入口。
- 如果 `buildOrdersCsv` 无其他调用，实施时删除该旧 helper 及对应测试；不能保留第二套绕过服务端权限的导出路径。

### 4.2 UI 状态、响应式与可访问性

| 状态 | 页面行为 |
|---|---|
| capability 加载中 | 显示设置导航骨架，不提前显示数据按钮 |
| 无权限 | 隐藏导航项；直接 URL 返回通用无权限状态，不显示店铺数量或导出信息 |
| 没有工单 | 模板仍可下载；导出按钮禁用并说明当前店铺无可导出工单 |
| 正在生成导出 | 按钮显示进度并防止重复提交，可取消尚未开始的请求 |
| 正在解析 | 显示文件名、大小和解析阶段，不允许同时再次上传 |
| 校验失败 | 按行/列显示错误，可下载错误报告并重新选择文件 |
| 预览完成 | 显示新增、更新、冲突、跳过和错误，并可筛选逐行差异 |
| 部分成功 | 成功、失败、跳过分别显示；提供只含失败行的报告 |
| 批次过期 | 禁止 apply，要求重新上传和预览 |
| 离线/网络错误 | 不缓存敏感文件正文；保留本地文件选择但要求联网后重新 preview |

响应式规则：

- 桌面端使用紧凑的纵向功能区和可滚动差异表，不做营销式卡片布局。
- 手机端按“模板/导出/上传/预览/应用”单列呈现；逐行差异改为可展开列表，不把宽表缩小到不可读。
- 主确认动作固定尺寸，长文件名换行或省略并提供完整 tooltip，不能挤压按钮。

可访问性规则：

- 文件输入、筛选和按钮有明确 label；图标按钮带可读名称。
- Preview 差异不用颜色作为唯一信息，同时显示 `新增/修改/清空/冲突` 文本。
- 错误摘要、进度和完成结果通过可访问动态状态区域宣布。
- 上传后焦点移到校验摘要；apply 确认后焦点移到结果标题。
- 差异表使用语义表头，所有流程支持键盘操作和 Escape 关闭确认层。

## 5. 文件设计

### 5.1 推荐主格式

推荐主格式为 `.xlsx`，因为工单有多条维修项目、字段说明和只读统计；单个 CSV 无法在不丢结构的情况下同时表达这些内容。

兼容格式为 UTF-8 CSV：

- 支持 SeaTable RIPARAZIONE 旧列名。
- 支持只含 `工单` 主表的简化导入。
- CSV 不承担历史记录和多维修项目完整结构；复杂数据使用 XLSX。

项目当前没有已确认的 XLSX 运行依赖。实施前必须单独完成依赖安全、许可证、维护状态和服务端运行兼容审查；该依赖不在本计划阶段自动加入。

### 5.2 “导出工单详情”工作簿

| Sheet | 用途 | 是否可导回 |
|---|---|---:|
| `工单` | 一行一张工单，保存匹配字段和当前业务字段 | Y，白名单字段 |
| `维修项目` | 一行一个维修项目，以工单 ID/外部行键关联 | Y |
| `字段说明` | 字段类型、是否必填、枚举、空白和清空规则 | N |
| `枚举值` | 当前允许的状态、类型、语言、布尔值等 | N |
| `工单历史` | 事件时间线的只读摘要 | N |
| `客户统计` | 本次导出范围内的客户聚合统计 | N |

消息正文、附件文件、附件 signed URL、客户签名和解锁凭据不进入工作簿。

### 5.3 “空白模板”工作簿

空白模板只包含：

- `工单` 空表头。
- `维修项目` 空表头。
- `字段说明`。
- `枚举值`。
- 单独的 `示例` sheet；示例数据必须是假数据，且 importer 永远忽略该 sheet。

模板包含 `模板版本`，后续字段变化时 importer 可以给出“模板版本过旧”而不是错误解释数据。

## 6. 工单主表字段合同

### 6.1 匹配与控制字段

| 字段 | 导出 | 空模板 | 导入用途 | 可编辑 |
|---|---:|---:|---|---:|
| 模板版本 | Y | Y | 解析兼容性 | N |
| 行动作 | Y | Y | `create/update/upsert/skip` | Y |
| RepairDesk工单ID | Y | 空 | 已有工单首选匹配 | N |
| 工单号 | Y | 空 | 当前店铺内第二匹配键 | 仅新建时可空 |
| 导出版本时间 | Y | 空 | 并发冲突检测 | N |
| 导出批次ID | Y | 空 | 验证文件属于当前店铺 | N |
| 来源系统 | Y | Y | `repairdesk/seatable/manual/其他` | Y |
| 外部记录编号 | Y | Y | 外部数据幂等匹配 | Y |

`store_id` 不作为可信导入字段。服务端始终使用登录账号的当前活动店铺；即使文件中有店铺标记，也只用于拒绝跨店文件，不能用来切换查询范围。

### 6.2 客户字段

- 客户ID，只读匹配。
- 客户姓名。
- 主电话。
- 备用电话，多个号码使用统一分隔规则。
- Email。
- 客户语言：`it/zh/en`。
- 首选联系渠道：`whatsapp/sms`。
- 同意短信、同意营销。
- 客户备注、营销备注。

客户资料是共享主档。若同一客户出现在多张工单中：

- 相同客户 ID/手机号在文件中的资料必须一致。
- 出现不同姓名或电话时，preview 标记为冲突，不能任意选最后一行。
- 更新共享客户主档时，preview 显示“会影响该客户的 N 张工单”。

### 6.3 设备字段

- 设备ID，只读匹配。
- 品牌、型号。
- IMEI/序列号。
- 设备备注。

设备匹配只在当前店铺的当前客户范围内进行。相同 IMEI 指向不同客户时必须进入冲突，不能自动合并。

### 6.4 工单业务字段

- 工单类型。
- 主状态、流程状态、异常状态。
- 配件状态、审批状态、通知状态。
- 故障描述、诊断结果。
- 技师。
- 内部标签。
- 留机/配件备注。
- 订单供应商、配件供应商。
- 质保文字、质保月数、质保修改原因。
- 取消原因、暂停原因。
- 创建时间、完成时间、交付时间。

日期规则：

- 新增历史工单可以提供原始创建时间。
- 已有工单的 `created_at` 默认只读，不能通过普通导回改写。
- 完成/交付时间必须与目标状态一致。

### 6.5 维修项目与金额

`维修项目` sheet 一行一个项目：

- 工单ID或外部行键。
- 项目序号。
- 项目名称。
- 项目价格。
- 币种，固定 `EUR`。
- 项目备注。

主表展示：报价总额、定金、已收金额、尾款、付款状态。

导入规则：

- 维修项目和定金可在白名单内修改。
- 报价总额由维修项目重新计算。
- 尾款和付款状态由系统重新计算。
- 已收金额、付款流水和退款记录只读，普通工单导入不得伪造或覆盖。
- 没有项目明细但有报价总额的新数据，可以生成一个“维修项目”占位项，preview 必须明确提示。

### 6.6 永不导入或默认不导出的敏感字段

- `store_id`、内部 RLS/权限字段。
- `created_by`、审计日志原文。
- 付款流水、退款流水、付款审核记录。
- 消息正文。
- 附件文件、附件路径、signed URL。
- 客户签名。
- 解锁方式、解锁值、图案序列。
- 原始 API payload 或数据库内部字段。

工单历史只导出事件类型、时间和操作者摘要；不作为回写来源。

## 7. 导入与覆盖规则

### 7.1 三种来源的默认模式

| 来源 | 默认模式 | 说明 |
|---|---|---|
| RepairDesk 工单详情导出文件 | 只更新 | 整理后导回，不自动新建 |
| RepairDesk 空白模板 | 只新增 | 从其他来源整理新数据 |
| SeaTable RIPARAZIONE | 新增并更新，但必须预览 | 通过来源编号防重复 |

老板可以在预览前更改模式，但 apply 页面必须再次显示选择结果。

### 7.2 工单匹配优先级

所有匹配都附加当前 `actor.storeId`：

1. `RepairDesk工单ID + 当前店铺`。
2. `工单号 + 当前店铺`。
3. `来源系统 + 外部记录编号 + 当前店铺`。

禁止用“客户电话 + 型号 + 日期”模糊匹配来覆盖已有工单。模糊相似只能作为人工提示，不能作为自动更新依据。

### 7.3 不清除规则

- 文件里没有出现的工单：完全不变。
- 文件里删掉的行：完全不变。
- 单元格空白：保留数据库原值。
- 未包含的列：保留数据库原值。
- 匹配不到的行：按所选模式新建或跳过，绝不先清库。
- 不支持 `delete` 行动作；作废只能显式改为合法取消状态并填写原因。
- 新 UI/API 禁止引用 `CLEAR_REPAIRDESK`、`clearRepairDeskDomain`、truncate 或批量 delete 路径。

### 7.4 显式清空

只有允许清空的可选字段可以填写 `__CLEAR__`。系统在 preview 中用高风险颜色列出每一个清空动作；以下字段永远不能清空：

- 工单 ID、工单号、客户主键、当前店铺。
- 客户主电话，除非同时提供有效替代电话并通过唯一性检查。
- 工单类型和故障描述等新建必填字段。
- 付款流水和审计信息。

### 7.5 版本冲突与“覆盖已有数据”

导出文件保存 `expected_updated_at`。导回时：

- 系统未变化：按预览字段更新。
- 系统在导出后已变化：该行标记 `conflict`，默认不应用。
- 主店主可以逐行选择“保留系统版本”或“用表格中的白名单字段覆盖”。
- 禁止一个全局按钮无差别强制覆盖全部冲突。
- 强制覆盖必须记录旧版本、新版本、字段名称、操作者和批次；审计不得保存不必要的完整 PII。

### 7.6 状态与历史修正

- 新建历史工单可按映射后的合法状态创建。
- 更新已有工单状态必须通过状态服务和合法转换规则，不直接写数据库状态列。
- 需要越过正常状态链的历史修正必须成为单独的主店主确认动作，并写入 `order_events`。
- 状态、金额、电话和共享客户主档变化在 preview 中单独高亮。

### 7.7 幂等与重复导入

- RepairDesk 导出文件重复导入，不得创建第二张工单。
- 外部数据必须提供稳定的 `来源系统 + 外部记录编号`；同一店铺内重复组合映射到同一工单。
- 同一文件 hash 和同一模式重复 apply 时，系统提示已处理批次，不重复写入。
- 每行独立记录成功、失败、跳过和冲突；修正错误行后可以重新预览。

## 8. 预览与应用流程

### 8.1 文件校验

- 校验扩展名、MIME、文件签名和模板版本。
- 设定文件大小、行数、sheet 数和解压后大小上限，防止超大文件或 XLSX zip bomb。
- 拒绝公式宏、可执行内容和未知 sheet 指令；只读取纯值。
- 标准化电话、金额、日期、布尔值和枚举。
- 所有错误都返回行号、列名、原始值摘要和修正建议，不返回内部堆栈。

### 8.2 Preview 输出

- 总行数。
- 新增、更新、跳过、冲突、错误数量。
- 每行匹配到的工单号。
- 每行字段级 before/after 差异。
- 客户共享主档影响范围。
- 报价、定金和状态变化。
- 跨店铺标记、版本冲突和重复来源编号。
- 可下载脱敏错误报告 CSV。

Preview 只读，不写任何客户、设备、工单、付款或状态数据。

### 8.3 Apply

- Apply 使用服务端 preview batch ID，不能让客户端提交一份重新解释的自由 JSON。
- batch 必须绑定 `actor.id + actor.storeId + file_hash + mode`，并设置短期有效期。
- Apply 前再次验证主店主身份、当前店铺、文件 hash 和工单版本。
- 按可控批次逐行处理；失败行不影响已验证的其他行，但汇总必须准确。
- 创建/更新通过现有 service/repository 业务规则，不直接拼接 SQL。
- 每张更新工单写 `order_events`，每个批次写审计摘要。

## 9. 店铺和账号隔离设计

### 9.1 请求边界

- API 不接受客户端提供的 `store_id` 作为数据范围。
- 服务端从登录会话解析当前活动店铺和成员身份。
- 数据查询全部强制 `.eq("store_id", actor.storeId)` 或等价 tenant guard。
- 客户、设备、供应商和工单子记录必须逐对象验证属于当前店铺。

### 9.2 多店铺账号

- 同一个主店主账号拥有多个店铺时，每次只导出当前活动店铺。
- 文件名和确认页清楚显示店铺名称。
- 切换活动店铺后必须重新加载 capability、清除上一店铺 preview batch 和相关缓存。
- 不提供“跨全部店铺导出”选项。

### 9.3 跨店文件

- RepairDesk 导出文件包含不可编辑的导出批次和店铺 scope 标记。
- 文件属于其他店铺时，preview 整批拒绝，不能自动切换或复制数据。
- 即使用户篡改 scope 标记，所有 ID 查询仍限制在当前店铺，不能读取或覆盖另一店铺对象。

### 9.4 下载安全

- 文件由服务端流式返回或使用短期私有下载，不生成长期公开 URL。
- 响应设置禁止共享缓存和内容嗅探。
- 浏览器端不持久化完整导出数据到 localStorage/IndexedDB。
- 审计记录 actor、store、筛选、行数、字段类别、时间和文件 hash，不保存完整导出正文。

## 10. 客户统计导出

客户统计保留为独立只读能力，仍然只对主店主开放。

统计内容：

- 总客户数。
- 复购客户数。
- 在修客户数。
- 未结清客户数和未结清金额。
- 有设备客户数。
- 待跟进客户数。
- 可营销客户数。
- 每位客户的工单数量、在修数量、总消费、未结清、设备数量、最后工单时间和下次跟进时间。

规则：

- 只统计当前活动店铺。
- 不跨店合并同手机号客户。
- 统计口径与客户页面现有 `CustomerStats`/客户列表服务端口径一致。
- 客户统计文件不能上传到工单 import apply。

## 11. 服务端与代码实施边界

### 11.1 权限基础

建议新增统一断言：

- `assertPrimaryStoreOwner(actor)`：查询当前 `stores.owner_user_id` 并验证有效 owner membership。
- `canManageOrderData`：由服务端 Store Context 返回，供设置页决定是否显示入口。

权限矩阵修改：

- `manager.order:export = deny`。
- `manager.customer:export = deny`。
- 新增 `order:import_preview`、`order:import_apply`，仅 owner 角色允许，并继续由 `assertPrimaryStoreOwner` 收紧。
- export/import 动作不可通过普通员工 permission grant 绕过。

### 11.2 推荐模块

- `src/features/orders/import/order-data-template.ts`
  - 字段合同、模板版本、枚举和字段说明。
- `src/features/orders/import/order-data-parser.ts`
  - XLSX/CSV/SeaTable 转换、标准化和行校验。
- `src/features/orders/server/order-data-export.service.ts`
  - 当前店铺详情导出和客户统计导出。
- `src/features/orders/server/order-data-import.service.ts`
  - preview、diff、冲突、apply orchestration。
- `src/features/orders/server/order-data-import.repository.ts`
  - 当前店铺匹配、批次记录、幂等引用和逐行写入。
- `src/features/settings/components/order-data-section.tsx`
  - 设置页唯一可视入口。

### 11.3 API 合同

- `GET repairdesk/orders/data/template?format=xlsx|seatable_csv`
- `POST repairdesk/orders/data/export`
- `POST repairdesk/orders/data/import/preview`
- `POST repairdesk/orders/data/import/apply`
- `POST repairdesk/customers/data/stats-export`

所有端点必须：

- 校验登录、当前店铺、主店主身份。
- 忽略客户端 `store_id`。
- 使用服务端筛选和分页读取全部目标工单。
- 写最小化审计日志。

## 12. 数据记录建议

为了实现幂等、预览、审计和可恢复性，建议增加：

### `order_data_batches`

- `id`, `store_id`, `actor_id`。
- `kind`: `export/import/customer_stats`。
- `source_format`, `template_version`, `file_hash`, `file_name`。
- `mode`, `status`, `summary`。
- `created_at`, `previewed_at`, `applied_at`, `expires_at`。

### `order_data_batch_rows`

- `batch_id`, `row_number`, `action`, `status`。
- `matched_order_id`, `matched_public_no`。
- `changed_fields`, `warnings`, `errors`。
- 最小化 before/after 版本信息，不保存完整客户正文。

### `order_external_refs`

- `store_id`, `source_system`, `external_record_id`, `order_id`。
- 当前店铺内唯一约束，保证外部数据重复导入不重复建单。

### 12.1 数据不变量和索引

- `order_data_batches.store_id`、`order_data_batch_rows.batch_id`、`order_external_refs.order_id` 必须有外键。
- `order_external_refs` 使用唯一约束 `(store_id, source_system, external_record_id)`。
- 所有批次和行表都保存 `store_id` 或通过不可变外键可证明 tenant；禁止只靠应用层推断。
- 建议索引：批次 `(store_id, created_at desc)`、行 `(batch_id, row_number)`、外部引用 `(store_id, order_id)`。
- 金额继续使用现有精度和 EUR 规则，不在导入表创建第二套金额真相。
- 文件正文不持久化到审计表；如确需临时保存，只能放私有存储并绑定 store/actor、短期过期和服务端授权下载。
- RLS 必须按当前店铺隔离，并进一步限制批量数据批次仅主店主可读/写；service role 路径仍需显式 tenant guard。

### 12.2 渐进迁移与恢复

采用 expand/migrate/contract：

1. Expand：新增批次、行和外部引用表/索引/RLS，不修改或删除现有工单字段。
2. Verify：在脱敏测试店铺验证约束、RLS、幂等、容量和查询计划；本功能不需要历史回填。
3. Release：先上线 capability 和模板，再导出，再 preview，最后单独启用 apply。
4. Contract：稳定观察后才评估是否删除旧 `buildOrdersCsv` 相关死代码；不删除历史业务数据。

回滚策略：

- 通过功能开关关闭设置页入口和 apply API，现有工单数据不受影响。
- 新表先保留用于审计与恢复，不能在回滚时立即 drop。
- 已应用行只能按记录的字段版本做补偿/撤销；存在后续人工修改时停止自动撤销并进入人工审查。
- 未取得生产数据量、索引构建耗时和恢复演练证据前，不得声称迁移安全或零停机。

批次元数据和行级差异的保留期限需要在实施批准包中确定；默认建议短期保留详细行错误、较长期保留脱敏批次摘要，避免无限保存客户数据副本。

任何新表、索引、RLS 或生产迁移都属于单独的 R3 数据变更；必须经过迁移历史 preflight、备份/恢复证明、Data/Security/QA 复核和老板对具体生产命令的批准。

## 13. 分阶段实施计划

### Phase 0：字段合同与样本验收

交付：

- 确认工单、维修项目、字段说明和枚举 sheet。
- 确认每个字段是可编辑、只读、可显式清空还是永不导出。
- 生成脱敏样本模板和解析单元测试。

退出条件：同一份字段合同同时驱动模板、导出和导入，不能出现三套列名。

### Phase 1：主店主权限与租户门禁

交付：

- `assertPrimaryStoreOwner`。
- manager/员工导出权限收紧。
- Store Context capability。
- 跨店、平台管理员、support 和伪造 store ID 拒绝测试。

退出条件：在任何真实数据导出能力上线前，服务端权限测试必须先通过。

### Phase 2：设置页唯一入口与空白模板

交付：

- `设置 > 工单数据`。
- 主店主可见，其他账号不可见。
- 下载空白 XLSX/SeaTable CSV 模板。
- 从订单页移除旧导出按钮和客户端导出路径。

退出条件：系统中只有设置页存在工单导入导出入口，模板中无真实数据。

### Phase 3：工单详情和客户统计服务端导出

交付：

- 当前店铺完整工单详情导出。
- 维修项目、字段说明、枚举、只读历史和客户统计 sheet。
- 筛选、分页/分批读取、文件流式响应和审计。

退出条件：主店主只能导出当前活动店铺；经理及其他角色 API/UI 均无法导出。

### Phase 4：导入预览

交付：

- RepairDesk XLSX、简化 CSV、SeaTable CSV 解析。
- 字段校验、当前店铺匹配、版本冲突和逐字段 diff。
- 下载错误报告。
- Preview 零业务写入测试。

退出条件：空白、缺行、重复行、跨店文件、错误金额和共享客户冲突都有明确结果。

### Phase 5：安全 Apply

交付：

- 只新增、只更新、新增并更新。
- 幂等来源引用。
- 白名单字段更新、`__CLEAR__`、状态服务、金额重算。
- order events、批次审计和逐行结果。

退出条件：重复导入不重复创建；任何场景都不会调用清库或删除未出现在文件中的数据。

### Phase 6：恢复、端到端验收和发布准备

交付：

- 导入历史、失败重试和批次结果查看。
- 对尚未被后续修改的行提供按版本保护的“撤销本批次”方案，或正式记录人工恢复 runbook。
- 全量静态、单元、集成、权限、租户和浏览器验收。
- 生产导入演练只使用脱敏测试店铺；生产发布另行批准。

## 14. 验收矩阵

### 14.1 UI

- 主店主在设置页看到四个数据操作。
- 其他角色看不到设置导航项。
- 订单列表不再显示导出按钮。
- 手动打开未授权设置 URL 不泄露数量、店名或文件信息。
- 桌面和手机都能完成模板下载、上传、预览和结果查看。

### 14.2 权限与隔离

- manager、technician、sales、viewer 导出/预览/apply 均为 `403`。
- 仅有 owner role、但不是 `stores.owner_user_id` 的账号也为 `403`。
- platform admin 和临时 support access 不能导出。
- Store A 主店主猜测 Store B 工单 ID 时，返回不可访问且不泄露是否存在。
- 同一账号拥有多店时，只处理当前活动店铺。
- 切店后旧 preview batch 失效。

### 14.3 导出与模板

- 导出是服务端全量/筛选导出，不受订单当前页分页影响。
- 空白模板只有字段、说明、枚举和假示例。
- 工单详情导出包含当前业务字段和匹配版本字段。
- 文件不包含解锁凭据、签名、附件 signed URL、消息正文或审计原文。
- 每次导出有最小化 audit 记录。

### 14.4 导入

- 导出一张工单、修改故障/设备/报价后导回，只更新该工单允许字段。
- 文件缺少其他工单时，其他工单不变。
- 空白单元格保留原值。
- `__CLEAR__` 只清除允许字段。
- 版本冲突默认不覆盖，逐行强制时有审计。
- 重复 apply 不重复创建。
- SeaTable 旧列能转换到标准字段。
- 跨店文件整批拒绝。
- 任意代码路径都不调用 `CLEAR_REPAIRDESK` 或清库函数。

### 14.5 建议验证

- `npm run lint`
- `npm run typecheck`
- `npm run test`
- `npm run build`
- 权限矩阵和主店主断言单元测试。
- tenant guard/跨店 ID 集成测试。
- 导出 -> 编辑 -> preview -> apply -> 再导出闭环测试。
- 设置页桌面/手机 Playwright 截图和无横向溢出检查。

## 15. 风险、批准与停止条件

本计划文档本身为 R2/L2；后续实施涉及权限收紧、客户 PII 批量导出、数据写入和可能的数据表迁移，实施/生产阶段按 R3 管理。

| 风险面 | 等级 | 原因 | 主要缓解 |
|---|---|---|---|
| 数据完整性 | R3 | 批量更新可影响大量客户/工单 | preview、白名单、版本检查、幂等、批次恢复 |
| 安全与隐私 | R3 | 导出包含整店 PII 和经营数据 | 主店主双重门禁、私有流式下载、审计最小化 |
| 租户隔离 | R3 | 错误 scope 可导致跨店泄露/覆盖 | actor-derived store、对象级 tenant guard、跨店测试 |
| 财务 | R2 | 报价和定金会影响余额 | 付款流水只读、服务端重算、差异高亮 |
| 可用性 | R2 | 大文件解析可能消耗资源 | 文件/行/sheet/解压上限、分批处理、超时与取消 |

必须单独批准：

- 修改真实角色权限行为。
- 新增 XLSX 依赖。
- 新增数据表、索引、RLS 或生产迁移。
- 对真实店铺执行首次批量导入或生产发布。
- 任何历史状态/时间的强制修正策略。

立即停止条件：

- 无法可靠验证 `owner_user_id`。
- 发现查询可以绕过当前 `store_id`。
- preview 与 apply 不是同一批次/文件。
- 导入需要调用现有清库脚本。
- 无法证明重复导入幂等。
- 文件或日志会暴露解锁信息、附件授权地址或不必要 PII。

## 16. 已采用的推荐默认值

1. 所有数据能力仅主店主账号可见和可用，导入也采用同一严格权限。
2. 主格式使用 XLSX，SeaTable/简化导入保留 UTF-8 CSV 兼容。
3. 导出工单详情和下载空白模板是两个完全独立的按钮和文件。
4. RepairDesk 导出文件默认 `只更新`；空白模板默认 `只新增`。
5. 空白保留原值，只有 `__CLEAR__` 才清空允许字段。
6. 缺行不删除，系统不提供表格删除工单。
7. 付款流水、解锁凭据、消息正文、附件和签名不通过工单表格回写。
8. 客户统计单独导出，不作为工单导入文件。
9. 所有导入导出入口只在设置页，订单页旧导出入口移除。
10. 正式 owner 转让后，权限随新的 `stores.owner_user_id` 转移。

## 17. 本计划明确不做

- 不做清库后重导。
- 不在订单页保留第二套导出入口。
- 不让 manager 或任何员工通过前端、API 或权限 grant 导出。
