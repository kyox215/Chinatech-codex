# 订单移动端筛选与队列加载性能优化计划

## 1. 结论与范围确认

本计划采用“先压缩首屏和补齐反馈，再消除真实慢路径”的两层方案。只加加载动画不能解决当前性能问题，因此 UI 和数据优化都列为必做工作包。

本次语义固定如下：

- 删除的是选择队列后出现的灰色摘要行，例如“队列：修好已通知”。
- 绿色“修好已通知”按钮是正式业务队列，必须保留并可正常查询。
- 搜索栏最右侧漏斗只从移动端删除；扫码按钮和桌面高级筛选保留。
- 列表下方绿色结果分组标题包含本页、总数和日期，不属于冗余摘要，继续保留。
- 不改变订单状态机、队列分类、权限、客户数据或桌面工作流。

## 2. 已验证基线与根因

规划证据以 `origin/main@119e4402` 为准。共享工作区 `main@cee5a1b4` 落后 29 个提交且包含大量无关改动；未来实施必须先获取最新远端，再使用隔离工作树，禁止在当前共享工作区直接修改这些订单文件。

已验证的 UI 事实：

- 移动搜索行目前是“搜索 + 扫码 + 漏斗”。
- 七个队列目前按两列四行排列，下面另有一行已选队列摘要。
- React Query 已暴露 `isPending`、`isFetching`、`isPlaceholderData`，并保留旧列表，但队列按钮没有 pending 状态。
- 当前可视 loading 主要服务于首次进入和文本搜索；队列切换只有不可见的 `aria-busy`。
- 旧列表在新队列请求期间继续存在，容易被误认为已切换后的结果。

已验证的性能根因，按优先级排序：

1. 每次队列请求先按 1,000 条批次读取该店全部订单和宽关联字段，再在服务端 JavaScript 中重复筛选、计数、排序，最后才切出 50 条。页面尺寸 50 并没有限制数据库和网络工作量。
2. 每次队列切换还重复读取相对稳定的 workflow 与 options；options 自身又包含供应商、技术员、成员等多次查询。
3. 每个队列有独立缓存键，第一次访问均为冷请求；默认预加载只覆盖默认队列。
4. 浏览器请求支持 AbortSignal，但服务端没有完整传递取消信号，快速连点后过期的 Supabase 工作可能仍继续执行。影响量需实测。
5. 认证/租户上下文和跨模块预加载也可能贡献延迟，但在采集 span 前不能把它们宣称为主因。

## 3. 推荐移动端布局

```text
┌ 菜单       订单管理 / 当前范围与数量       ＋ ┐
│ [ 搜索订单、客户、手机………………… ][扫码] │
│ [ 待处理 ]       [ 历史 ]       [ 全部 ]   │
│ [                 全部待办                 ] │
│ [ 处理中 ]       [ 下单 ]       [ 到货 ]   │
│ [到货已通知]     [ 修好 ]     [修好已通知] │
└─────────────────────────────────────────────┘
  正在加载“下单”队列…
  结果分组标题
  工单卡片
```

布局规则：

- 菜单、新增、搜索、扫码保持约 40px 高；不通过缩小主要触摸目标换取空间。
- 删除漏斗后，搜索行使用“自适应搜索框 + 40px 扫码”两列，搜索输入获得更多宽度。
- “待处理 / 历史 / 全部”控制总高控制在 34–36px。
- “全部待办”保持全宽；六个业务队列在 360–767px 使用三列两行，每格约 40px 高、4px 间距。
- 小于 360px 回退两列，禁止横向滚动；大于等于 768px 保留桌面布局与高级筛选。
- 删除整个移动端已选摘要容器，不留下空白或占位。
- 搜索反馈和队列切换反馈放在可滚动内容顶部，不让固定头部动态变高。
- 同步更新初始 Skeleton 的矩阵和高度；继续使用现有 ResizeObserver 计算真实头部偏移，不能另写一套固定 padding。

量化目标：

- 390×844 视口下，安全区以外固定头部不超过约 300px。
- 相比实施前实测基线至少减少 50px 或 15%，以较严格者作为验收参考。
- 18% 作为优先优化目标，但不能以缩小触摸目标或截断核心队列名称换取。
- 首屏能完整看到第一张订单卡，并尽量露出下一张卡的一部分。

## 4. 队列切换状态合同

### 4.1 用户点击后的即时反馈

- 点击“下单、到货”等队列后，目标卡片在 100ms 内切换选中态，并在数量位置显示 Spinner 或小型进度状态。
- 列表顶部显示唯一文案，例如“正在加载‘下单’队列…”，使用 `role=status` 与 `aria-live=polite`。
- 新请求期间保留旧数据以避免整页闪白，但旧列表降低透明度并禁止点击；结果标题不能使用“新队列名称 + 旧队列数量”的组合。
- 同一队列重复点击不发重复请求；其他队列仍可点击，采用最后一次选择生效。
- 切换范围或队列时分页重置为 1，并回到列表顶部。

### 4.2 状态矩阵

| 状态 | 可视反馈 | 数据语义 |
|---|---|---|
| 首次加载 | 与新紧凑布局一致的 Skeleton | 不显示空态 |
| 队列切换 | 目标按钮 Spinner + 顶部加载条/文案；旧列表淡化禁用 | 不把旧结果伪装成新结果 |
| 缓存命中 | 直接显示，必要时只做非阻塞“更新中”提示 | 已缓存数据可用 |
| 后台刷新 | 小型“正在刷新” | 当前列表保持可操作 |
| 新队列为空 | “下单队列暂无工单” + “查看全部待办” | 成功空态，不是错误 |
| 切换失败 | “加载‘下单’失败” + 重试；回到最近成功队列 | 不保留错误的新选中标签 |
| 刷新失败 | “刷新失败，正在显示最近数据” + 重试 | 继续显示可信缓存 |
| 离线 | “当前离线，显示最近数据”；无缓存时明确错误 | 禁止无限 Spinner |
| 快速连点 | Spinner 跟随最后一次选择 | 最后一次请求才允许提交 UI |

建议在屏幕层增加显式 `pendingListIntent`，区分 queue、view 和 page 切换；文本搜索继续使用现有独立 debounce/loading 状态，避免重复播报。

## 5. 分阶段实施合同

### WP-00：基线、隔离与观测

目标：不凭感觉宣称“变快”。

- 从实施时最新 `origin/main` 建立隔离工作树，确认用户截图对应的现状仍存在。
- 在 100、1,000、10,000 条代表性数据量下记录六个队列的冷/热请求。
- 客户端记录点击、首个反馈、请求完成、首帧可用；服务端记录 auth、列表查询、JS 处理/计数、workflow、options、序列化。
- 记录 TTFB、总耗时、读取行数、返回体字节和取消次数；日志不得包含搜索词、客户姓名、电话或其他 PII。

退出条件：形成可复现的 before 基线；没有基线不得关闭性能任务。

### WP-01：移动端密度与删除项

目标：先获得明确、低风险的空间改善。

- 删除移动端漏斗 Sheet/按钮，搜索行改为搜索 + 扫码。
- 删除移动端已选队列摘要；桌面 active-filter chips 保持。
- 队列网格改为三列两行业务队列，小屏回退两列。
- 同步 Skeleton、固定头部测量、滚动偏移和无障碍名称。

退出条件：390px 头部达到高度目标；320/390/430px 无溢出；业务队列、扫码和桌面筛选仍可用。

### WP-02：切换 loading 与错误语义

目标：点击后马上知道系统在工作，而且不会误操作旧数据。

- 增加 `pendingListIntent`、目标队列 Spinner、进度文案和列表 `aria-busy`。
- 保留但淡化/禁用旧列表，成功后原子替换；失败回到最近成功队列并提供重试。
- 验证最后一次点击生效、过期请求取消/忽略、相同队列不重复请求。
- 搜索、分页、后台刷新和离线状态使用互斥而完整的文案。

退出条件：1.5 秒人工延迟下，100ms 内出现反馈；快速点“下单→到货”最终只显示到货。

### WP-03：客户端缓存与请求去重

目标：减少重复网络工作，不制造预取风暴。

- 把 workflow/options 拆为 store-scoped 稳定查询，初始加载可保留兼容聚合；队列切换只请求页面与计数。
- 稳定元数据初始建议缓存约 5 分钟，并在设置、角色、店铺和工作流变更时精确失效。
- 评估订单队列 30–60 秒专用 stale time，前提是订单变更和 realtime invalidation 测试通过。
- 可在 pointer-down 对“这一次将点击的队列”启动同键预取；在后端 fetch-all 修复前禁止空闲预取全部六个队列。
- 去掉与 queue-summary 重复或竞争的预加载，跨模块预加载延后到队列可用或浏览器空闲。

退出条件：热缓存切换不超过 300ms；请求数和并发低于基线；实时更新不回归。

### WP-04：无迁移的服务端查询减负

目标：消除“全店宽表取回后再切 50 条”的主瓶颈。

- 先把 active/archive 的明确状态谓词前移到 Supabase 查询，避免默认待处理队列读取完成/取消历史。
- 页面明细使用只含卡片所需字段的窄投影，禁止 `customer(*)`、`device(*)`、`supplier(*)` 式宽展开。
- 明细查询在数据库侧排序、分页，只返回最多 50 条；队列/结果计数使用另一条窄分类投影并与明细并行。
- 保留旧 aggregate/list 路径作为兼容回滚；先不改 schema、不新增索引。
- 测量 auth-context；只有证据表明它显著时，才另开安全评审处理并行化/缓存。

退出条件：明细读取行数不随全历史规模增长；API p95 与负载预算达标；权限与租户隔离回归通过。

### WP-05：可选数据库结构优化（单独审批）

仅当 WP-04 在代表性数据量下仍未达到目标时启动：

- 设计 tenant-safe `orders_queue_page_v2` 类 RPC，在 SQL 中完成与前端分类函数完全一致的队列分类、计数和分页。
- 使用代表性数据执行 `EXPLAIN (ANALYZE, BUFFERS)`；只根据查询证据添加索引。
- 独立复核 RLS、grants、调用者身份、security invoker/definer、跨店隔离和回滚。
- 生产迁移前需 Owner 明确 D3 批准、dry-run、备份/回退方案和应用后元数据验证。

退出条件：DATA、SEC、QA 独立通过且 Owner 已批准；旧 API 路径保留到生产证据稳定。

### WP-06：完整验证、视觉证据与文档

- 组件测试：移动端无漏斗、无队列摘要、所有业务队列仍存在；pending/aria/失败/重试状态。
- 查询测试：相同队列去重、最后点击生效、缓存恢复、精确失效、AbortSignal 链路。
- repository/router 测试：筛选/分页发生在映射前；不执行全历史宽明细读取；workflow/options 不随每次切换重复。
- E2E：390×844、430×932、768×1024 和桌面 1280/1440；慢 1.5 秒、错误、离线、快速连点。
- Chromium 覆盖完整视口矩阵；WebKit 至少覆盖 390×844 与 430×932。
- 性能采样使用 production build，先预热 5 次、再采样至少 30 次，并记录中位数与 p95。
- 回归：权限、租户、技术员可见性、财务/联系方式投影、realtime invalidation、扫码、桌面筛选。
- 质量门禁：`npm run lint`、`npm run typecheck`、`npm run test`、`npm run build`。
- 视觉证据：移动端空闲态、加载态、完成态以及桌面筛选保留态；使用测试数据并遮蔽 PII。

## 6. 性能预算

以下都是实施目标，不是本次规划已经测得的结果：

| 指标 | 目标 |
|---|---|
| 点击到可见反馈 | ≤100ms |
| 常见交互 INP 风格预算 | ≤200ms |
| 已缓存队列恢复 | 理想 ≤150ms；上限 ≤300ms |
| 未缓存队列 API TTFB | p50 ≤350ms；目标 p95 ≤500ms；发布上限 ≤800ms |
| 未缓存队列可用结果 | p50 ≤500ms；p95 ≤1s |
| 数据库明细查询 | p95 ≤250–300ms |
| 明细行数 | 每页 ≤50，不随全店历史增长 |
| 原始列表负载 | 目标 ≤100–150KB，按基线调整 |

若实际环境因网络条件无法达到绝对时间，必须同时证明：相对基线显著改善、点击反馈仍在 100ms 内、服务器读取规模不再随全历史线性增长。

- 390×844 下固定头部不超过约 300px，且比 before 至少降低 50px 或 15%。
- 320、390、430px 无横向滚动；360px 起使用三列业务队列。
- 移动搜索栏只保留搜索和扫码；桌面高级筛选仍可用。
- 页面不再出现灰色“队列：修好已通知”，绿色“修好已通知”队列与 API 分类保持原样。
- 绿色结果分组标题和本页/总数/日期保持。
- 1.5 秒延迟下，点击后 100ms 内出现目标高亮、Spinner 和文字反馈。
- 加载期间旧卡片不可点击、不可误标；成功、空、失败、离线、刷新均无永久 Spinner。
- 快速点击“下单→到货”只提交到货结果；相同按钮不重复发请求。
- 热缓存切换 ≤300ms；未缓存 API p95 目标 ≤800ms；明细最多读取 50 条。

- focused tests、lint、typecheck、test、build 全部通过并有截图证据。

## 9. 风险与回滚

- 隐藏移动漏斗后，若桌面高级筛选在窗口缩窄时仍生效，需要在内容区仅提示“有高级条件生效/清除”，不能恢复冗余队列摘要。
- 三列标签在大字体或未来翻译下可能截断；完整 `aria-label` 与小于 360px 两列回退是硬要求。
- 旧列表若只保留而不淡化/禁用，会发生语义错配和误点；这是 WP-02 的 P0 验收项。
- 预取所有队列会把当前 fetch-all 问题放大；后端修复前明确禁止。
- 稳定元数据缓存可能延迟权限/设置变化；必须有精确失效和安全回归。
- SQL/RPC 分类可能与 TypeScript 分类漂移；必须共享契约样例并做双实现一致性测试。
- 任意 RPC/grant 错误都可能造成跨租户数据泄漏，因此 WP-05 独立审批、独立安全审查。

回滚分层：

- WP-01 可只回退移动头部、Skeleton 与布局常量。
- WP-02/03 可回退 pending state 和 query/cache 选项，恢复旧 `keepPreviousData` 行为。
- WP-04 保留旧 aggregate/list 兼容路径，可通过开关退回；第一轮不需要迁移。
- WP-05 若获批，旧路径在生产证据稳定前不得删除，数据库对象必须有向下迁移/禁用方案。

## 10. 执行顺序与批准边界

推荐实施顺序：WP-00 → WP-01 → WP-02 → WP-03 → WP-04 → WP-06。WP-05 不是默认实施内容，只在实测不达标且 Owner 另行批准后插入。

本计划完成不代表已经改动页面或获得发布授权。Owner 说“开始”后，可在 R2/L2 范围执行 WP-00 至 WP-04 与 WP-06；数据库 RPC/索引、生产应用、提交推送和部署仍需各自的明确授权。
