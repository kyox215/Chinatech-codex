# Memory Delta

Task-local conclusions:

- Shared IMEI candidate parsing now lives in capture model code and should be reused by future camera/OCR/manual IMEI flows.
- Image barcode/OCR capture must clear its processing state even when recognition succeeds but requires user candidate selection.
- Browser E2E can verify the new-order IMEI dialog with `REPAIRDESK_E2E_ORDER_AUDIT=1`; real camera and Safari still require manual device testing.
- Do not add OCR dependencies such as Tesseract.js without a separate Owner-approved dependency/security decision.
- Future follow-up: consider service-side identifier validation for `device_imei` / `serial_or_imei` to cap length and allowed characters.
- `TextDetector` is a conditional browser capability, not a guaranteed Safari OCR solution. Product copy and验收 must say pure numeric photo OCR works only where browser-native OCR is available unless a separate OCR dependency/service is approved.
- `ImeiScannerField` must stop delayed ZXing controls after dialog close; keep the delayed-control regression test if refactoring camera startup.
- IMEI capture UI should not show raw browser/library/server `error.message` for unknown camera, image decode, OCR, or save failures. Use whitelist mappings and generic fallback copy.
- IMEI automated E2E is scoped by `tests/e2e/imei-capture.playwright.config.ts`; specify `imei-capture-ui.spec.ts` so unrelated E2E files do not mix into this gate.
- WebKit Playwright browser may need `npx playwright install webkit` on a fresh machine before Safari-engine E2E can run.
- iPhone gallery uploads may arrive as `image/heic`, `image/heif`, or with an empty MIME type but `.heic` / `.heif` extension. IMEI image validators should allow these through while keeping decode failure safe and recoverable.
- Playwright device descriptors (`Pixel 7`, `iPhone 15`) improve mobile browser coverage, but they are not a substitute for real camera hardware and permission testing.
- Uploaded-image barcode decoding can hang on Chromium for non-barcode images; keep timeout protection and fallback to OCR/manual entry.
- Blank `device_imei` inline patches should be rejected in UI, API schema, repository, and mock API because empty snapshots can be masked by linked-device fallback values.
- IMEI-only order patches need invariant coverage proving customer linkage, device linkage, unlock PIN/password, contact fields, notes, warranty, fault prices, and finance fields are preserved.
- Order-detail route-level E2E currently needs a reliable active-store setup before it can prove persisted detail save; component + mock/API tests are the current stable coverage.
- Same-store role authorization for `order/update` and `order/patch` is outside this IMEI capture slice and should be handled as a separate security hardening task.
- IndexedDB offline drafts intentionally preserve order context and currently include normalized IMEI. Treat this as a privacy/retention decision rather than an accidental scanner leak.
- Keep direct regression coverage for camera startup error variants (`NotAllowedError`, `NotFoundError`, `NotReadableError`, `OverconstrainedError`, and insecure-context `TypeError`) because mobile Chrome/Safari failures often arrive through these browser-specific branches.
- Keep uploaded-image barcode timeout coverage: ZXing image decode can hang on non-barcode photos, and the expected behavior is local OCR fallback or manual entry rather than a stuck processing state.
- Live camera capture currently verifies barcode/QR decoding, not continuous OCR over camera video. Pure numeric OCR is provided through uploaded/captured image files when the browser exposes native `TextDetector`.
- Mobile real-camera validation needs HTTPS; `localhost` is enough for desktop Chrome/Safari, but `http://<LAN-IP>` is expected to fail mobile camera access.
- Inline `device_imei` patch validation should remain stricter than create/full edit optional text: nonblank, max 64 characters, and serial-safe characters only.
- Do not open public tunnels for device QA without explicit owner approval because they expose the local preview through a third-party service.
- Keep camera startup fallback coverage: when `facingMode: environment` is overconstrained, retry `video: true` before showing an error.
- Do not duplicate a numeric IMEI as a generic serial candidate when `includeGenericSerial` is enabled; duplicate same-value candidates make single scans require unnecessary manual selection.
- Fake-camera E2E now proves Chromium media-stream startup plus ZXing QR decode into the new-order IMEI field. It still does not prove physical camera hardware, mobile permission prompts, rear-camera lens selection, or mobile OS gallery behavior.
- When generating Y4M fake-camera frames with sharp, call `.removeAlpha()` before `.raw()`; otherwise RGBA data will be misread as RGB and the QR frame becomes distorted.
- IMEI E2E configs that rely on `REPAIRDESK_E2E_ORDER_AUDIT=1` should run `next dev` on `localhost`, not `next start` on `127.0.0.1`; production `next start` correctly rejects mock auth bypass when Supabase browser auth is absent.
- Order-detail IMEI save-refresh now has a route-level E2E through `/orders/ord_1`, the device-panel read-mode popover, `/api/repairdesk/order/patch`, and page reload assertion.
- Server-side order write routes should call the existing permission matrix before writes. Current IMEI task enforces it for `orders/create`, `order/update`, and `order/patch`, with field mapping for inline patch intake vs repair updates.
- Create, full edit, and inline patch IMEI / serial validation should stay consistent: blank is allowed only for create/full edit compatibility; nonblank values are trimmed, max 64 characters, and limited to serial-safe characters.
- Mobile order-detail OCR must keep a timeout wrapper around browser-native `TextDetector` and image decode work so the bottom sheet cannot remain stuck in `识别中...`.
- Real-device IMEI QA should generate local labels with `npx tsx scripts/generate-imei-real-device-fixtures.ts`; use the generated QR/text label files instead of production IMEI/customer data.
- Keep `tests/e2e/imei-upload-real-qr.spec.ts` as the non-mocked uploaded-image barcode gate: it proves a generated QR PNG uploaded through the browser can be decoded by `@zxing/browser` across Chromium/WebKit projects.
- Keep `tests/e2e/imei-order-detail-upload-real-qr.spec.ts` as the order-detail persistence gate: it proves uploaded QR decode, `/api/repairdesk/order/patch` save, page reload, and detail-page visibility for the saved IMEI.
- `order/update` must remain field-aware. Full-update payloads touching repair, unlock, warranty, quote, or deposit fields require stronger permissions than `order:update_intake`; if sales/frontdesk needs those edits, add explicit scoped permissions instead of weakening the full-update guard.
- `order/finance` must require `payment:adjust`; do not leave finance edits protected only by UI visibility.
- Inline `device_unlock` patch is a repair/sensitive write, not a plain intake edit. New-order creation can still collect unlock metadata through the create path, but existing-order unlock edits need stronger permission design.
- Full-edit blank IMEI remains unresolved product semantics. Inline patch rejects blank, but full edit still allows blank for compatibility and may later display linked-device fallback. Decide whether blank means unknown, clear, or inherit before advertising “clear IMEI” as supported.
