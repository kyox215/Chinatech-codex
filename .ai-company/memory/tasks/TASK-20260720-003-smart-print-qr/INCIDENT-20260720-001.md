# Incident — first smart-QR migration apply rejected

- **Incident commander:** RepairDesk Integration Lead
- **Severity:** SEV-3 safe release-gate failure; no customer or data impact
- **Started:** 2026-07-20T20:44Z
- **Contained:** 2026-07-20T20:48Z

## Timeline

1. Final linked dry-run listed only `20260720190759_repair_order_customer_status_links.sql`.
2. Production apply stopped on the migration's first `create table`: PostgreSQL rejected `order_id text` referencing UUID `repair_orders.id` with SQLSTATE `42804`.
3. The feature flag remained off and no application push/deployment had occurred.
4. A linked migration-list check confirmed `20260720190759` was not recorded remotely.
5. The migration and both RPC contracts were corrected to UUID.
6. A clean PostgreSQL 17 UUID-schema replay passed migration execution, RLS/grants, concurrent issue uniqueness/audits, forced audit-failure rollback, revoke atomicity and combined limiter invariants.

## Root cause and contributing factor

The original replay fixture declared `repair_orders.id` as text rather than matching the production UUID schema. The database migration gate correctly prevented an incompatible foreign key from being created.

## Recovery and prevention

- Keep the additive migration pending until corrected dry-run and tests pass.
- Permanently assert `order_id uuid not null` in the migration test.
- Future schema replays must copy the referenced production column type, constraint and composite key instead of using a simplified type.
- Do not enable the feature flag or deploy application code before the database migration is verified.
