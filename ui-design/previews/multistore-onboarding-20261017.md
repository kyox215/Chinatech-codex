## 客户实际使用流程

| 使用者 | 流程 | 授权边界 |
| --- | --- | --- |
| 独立店主 | 注册个人账号 → 验证邮箱 → 填店名 → 创建空门店 → 进入后台 | 只成为自己新建门店的老板，不能指定已有门店或他人老板身份 |
| 员工 | 取得店主邀请链接/二维码 → 注册或登录并验证邮箱 → 核对目标店 → 主动申请 → 负责人审核 | 申请和验证邮箱均不自动入店；审核前不能读取该店业务资料 |
| 已加入多店的成员 | 登录 → 我的门店 → 选择获授权门店 | 每次请求核当前会话、目标店、有效成员和具体权限 |
| 邀请失效/申请被拒 | 查看本人目标店、日期和状态 → 向负责人索取新邀请 | 不公开搜索店名加入，不通过旧邀请绕过审批 |
| 忘记密码 | 请求重置邮件 → 在发起流程的浏览器打开链接 → 设置新密码 → 重新登录 | 原密码及重置前会话失效；跨浏览器确认保留安全恢复提示 |

邀请候选跨注册、刷新和同浏览器新标签保留，得到服务端 Cookie 往返确认后才清除原链接哈希。候选保留不代表提交申请。申请、建店与审核结果不明时保留原请求标识和输入，沿原请求核对，不自动重复创建。

审核页显示员工邮箱和姓名；负责人应核对邮箱再批准。店长只能分配自己持有且可转授的权限，不能授予老板身份或转授“管理员工权限”；默认勾选同样取可分配权限交集。

## 已实施的界面与行为

- 我的门店：成员门店、本人申请的店名/时间/状态、创建与加入入口；手机低频表单可折叠。
- 邀请与审核：准确的有效/已使用/撤销/过期状态，待审与历史分开计数，邀请和申请都有后续分页。
- 未知结果：刷新后回显原审批角色、权限、申请和请求标识；原申请离开当前列表后仍可核对原提交。
- 失效邀请：继续拒绝批准；负责人可拒绝并归档原待审申请，员工能刷新看到结果。
- 商品列表：保留销售状态、新机/翻新分类和完整业务事实；搜索与筛选按钮同排，低频筛选默认收起，手机展开两列、桌面一排，保留 URL、清空、计数和键盘操作。
- 客户列表/详情沿用原控件并缩减局部间距。手机维修下拉框统一到16px；主要手机操作至少44×44px。
- 沿用768px桌面/767px手机布局、原侧栏和 B 方案反馈。刷新保留原内容，真实请求显示紫色细线；网络或异常响应使用受控三语提示。

未引入新主题、控件库、全局顶栏或底部主导航。普通输入、选择、多选、导航和通知继续复用 InputControl、SelectControl、MultiChoice、NavigationLink、Toast 与现有语义 token。

## 安全与生产权限修复

业务继续使用共享 Supabase 基础设施，通过不可变 store_id、服务端受限角色、RLS、事务、成员权限和私有附件隔离；不是每家店各分配一套物理数据库。申请人店名投影只读取 auth.uid() 本人的申请，不放宽 stores 的 RLS。

本轮额外发现并先行关闭了旧 public API 的客户端访问入口：精确移除15张旧表和1个序列的 anon/authenticated 权限，保留旧行、运维权限、Auth 触发器和现有业务规则。实际生产迁移为 `20261017135700_lock_legacy_public_api`，源 SQL SHA256 为 `ecdf8e25d72478b83d0e910b28b838dd0fbb8642a44de6295075d7eaf700f080`。

根独立核对：35项数据行数和摘要保持；RLS、默认权限、角色、触发器及函数保持；实际匿名旧 REST 返回401/42501，既有正式账号仍可读取门店。有效权限检查计入继承/PUBLIC，15表及序列的匿名和普通登录角色均无权限，service_role 保留。新账号真实生产 JWT 的直接 REST 请求尚未单独执行，不将元数据或本地 JWT 测试冒称该项实测。

邀请和游标使用独立服务端签名密钥，生产配置已加密保存；未使用数据库凭据签名。客户端构建扫描未发现本地签名密钥。游标绑定账号、会话、门店、筛选与权限版本，不能跨范围使用。

数据库备份与附件备份分开保留。既有全库 archive 6,874,462B 的 SHA256 `d14e9d09fc78f5eb4ec607166db1aad8cd98d3c6decde3ce535c229af1881af8` 已重新核对；权限切换前另存新鲜 ACL、逆向权限脚本与行摘要。**未完成全库恢复演练**；本地缺失的历史91表切换摘要对不作为独立验收证明。

生产 Security Advisor 仍有5条旧 public invoker 函数的 search_path WARN；当前新 schema 无 WARN。默认拒绝且无 policy 的 private 表属于有意封闭，不为消除 INFO 放宽权限。后续维护参考[官方 search_path 整改说明](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable)。扫描不能替代实际角色/API隔离测试。

## 容量快照与收费建议

2026-10-17 13:10Z聚合SQL、13:11Z控制台只读快照；不是持续监控。

| 项目 | 结果 | 口径 |
| --- | --- | --- |
| Supabase数据库磁盘 | 已分配8GB，总占用约0.46GB/6% | 包含Database/WAL/System，控制台约数 |
| Postgres数据库 | 127,470,739B，约121.57MiB | pg_database_size，不能与磁盘总量混算 |
| 新业务表及索引 | 11,321,344B，约10.80MiB | 新业务两个schema合计，不是单店额度 |
| Storage | 5条对象元数据，共238,348B | 数据库记录size汇总，不代表Storage套餐总上限 |
| 计算规格 | NANO/t4g.nano，界面最多0.5GB内存 | 磁盘空闲不能证明可承载无限并发 |
| 当前生产权益 | 1店；内测总上限20；每店附件1,000,000,000B/有效成员5，含老板 | 附件权益不是独享1GB数据库；账号每日最多创建3店 |

网站前端由Vercel托管，未测得独立VPS剩余磁盘；Vercel详细Usage/流量账单此前受2FA设置页阻挡，未绕过安全步骤。当前空间没有立即扩容依据，也未扩大规格或改变费用上限。

建议保留附件与有效成员的服务端限制：80%提示，满额仅阻止新增占用，保留既有资料读取、收款和交还。先积累各店实际附件/预留容量、成员数及数据库增长，再确定套餐。数据库索引、Auth和共享日志按平台总量管理，不能当成每店独立磁盘计费。

收费前先确定权益版本、账单、续费、宽限期、降级后的读取/导出及数据保留规则，再接支付。超额或欠费不自动删除店铺、历史和附件。当前未接支付、未设置价格、未自动扣费。

后续优先项：正式小样及实体手机邮件/软键盘/相机验收；恢复演练；依据实际负载评估计算规格。体验上可进一步折叠长申请/邀请历史，并考虑邀请绑定指定邮箱，减少误用；这些没有被冒称为本轮已实现能力。
