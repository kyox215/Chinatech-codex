# company-task-intake

## 目标

把自然语言目标转换为可执行、可验证、可分派的任务合同，防止团队在目标、边界和完成定义不清时开始实施。

## 输入

- 老板原始任务与业务价值
- 现有 ACTIVE_CONTEXT 与 PROJECT_MEMORY
- 明确的期限、预算、合规或技术约束
- 当前代码与系统事实（若已知）

## 执行流程

1. 原样保留老板目标，区分“要求”“偏好”“假设”和“建议”，不得把建议提升为硬性要求。
2. 生成任务 ID，并判定 T0–T3 规模。T0 可不创建完整档案，其余创建 `.ai-company/memory/tasks/<TASK_ID>/`。
3. 定义业务结果、用户/利益相关方、范围内、范围外、不可破坏项、依赖、预算和时间约束。
4. 把完成定义改写为可观察验收标准；每条标准必须能由测试、运行结果、文件证据或人工验收证明。
5. 列出已知事实、未经验证假设、未知项和冲突；非阻塞未知项采用保守默认，阻塞未知项进入批准包。
6. 识别潜在数据、API、权限、财务、法律、生产和客户影响，并交给 `$risk-autonomy-classify`。
7. 把任务档案、验收标准与下一步写入任务记忆；不要在接收阶段宣布方案已批准。

## 必须产出

- 任务章程
- 范围内/外清单
- 可验证验收标准
- 事实/假设/未知项表
- 后续 Skill 路由建议

## 门禁与停止条件

- 没有业务结果或验收标准时不得进入实施
- 高风险未知项必须升级，不用猜测补全
- 不得把“页面出现了”当成端到端业务完成

## 记忆更新

创建或更新 TASK.md、ACTIVE_CONTEXT.md 和任务的 MEMORY_DELTA.md。

## 通用执行约束

- 先读当前目录适用的 `AGENTS.md` / `AGENTS.override.md`。
- 只加载与任务相关的政策和记忆；避免把整个制度包塞入上下文。
- 对事实附文件、符号、测试、日志或正式决定证据；不把推断写成事实。
- 遵守单一写入者、最小权限、可逆优先、秘密最小化和不覆盖用户改动。
- 当范围、风险、目标环境或关键假设变化时，暂停并重新分类。

## 建议输出格式

```markdown
# 结论
# 已验证事实与证据
# 假设 / 未知 / 冲突
# 决策或建议
# 风险与审批点
# 验证结果
# Memory Delta
# 下一步
```
