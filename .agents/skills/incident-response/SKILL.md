# incident-response

## 目标

在压力下以统一指挥、最小伤害和事实时间线处理事故，避免边修边扩大影响或过早归因。

## 输入

- 告警/报告
- 影响范围
- 日志和指标
- 最近变更
- 系统与数据恢复能力

## 执行流程

1. 指定 Incident Commander，声明严重级别、影响、开始时间、沟通渠道和当前已知/未知。
2. 优先保护人员、数据和客户：隔离、降级、关闭开关、限流或回滚；高风险动作遵循紧急权限。
3. 建立事实时间线，保存必要日志、版本、配置和操作证据；不在事故中清理关键证据。
4. 持续评估爆炸半径、数据完整性、安全性和客户影响；定时发布简洁状态。
5. 恢复前验证修复/回滚、依赖、数据校验和监控；恢复后观察稳定窗口。
6. 事故结束后做无责复盘：根因、促成因素、检测/响应缺口、哪些控制有效。
7. 把行动项变成有 owner/期限/验收的任务，更新运行手册、测试、告警和记忆。

## 必须产出

- 事故声明
- 时间线
- 缓解/恢复记录
- 客户/内部沟通
- 复盘和行动项

## 门禁与停止条件

- 事故中不做无关重构
- 未经验证不宣布恢复
- 安全/隐私事件按法务和通知政策升级

## 记忆更新

创建 incident 记录，更新 LESSONS、风险、runbook 和相关能力评估。

## 通用执行约束

- 先读当前目录适用的 `AGENTS.md` / `AGENTS.override.md`。
- 只加载与任务相关的政策和记忆；避免把整个制度包塞入上下文。
- 对事实附文件、符号、测试、日志或正式决定证据；不把推断写成事实。
- 遵守单一写入者、最小权限、可逆优先、秘密最小化和不覆盖用户改动。
- 当范围、风险、目标环境或关键假设变化时，暂停并重新分类。

## 建议输出格式

```markdown
# 结论
# 已验证事实与证据
# 假设 / 未知 / 冲突
# 决策或建议
# 风险与审批点
# 验证结果
# Memory Delta
# 下一步
```
