# agent-team-compose

## 目标

把公司部门模型映射为真正有独立交付物的子 Agent，避免所有角色每次都参加，也避免并行写入冲突。

## 输入

- 任务规模与风险
- 受影响领域
- 可用 `.codex/agents/*.toml`
- 能力登记与上下文预算

## 执行流程

1. 先判断是否值得创建子 Agent；T0、顺序强依赖或启动成本高于收益时保持单线程。
2. 选择 2–4 个互补的只读角色进行探索或审查；每个角色必须解决不同问题。
3. 为每个工作包写明目标、输入、范围外、输出结构、证据要求、停止条件和时间/Token 边界。
4. 显式要求 Codex spawn 指定 Agent、等待全部结果后再合并；不要仅写“交给某部门”。
5. 默认只允许一个 `implementer` 修改业务代码；Reviewer 不修自己的发现，Memory Steward 后置顺序运行。
6. 主线程对结论去重、对比证据、处理冲突；不能简单拼接多个 Agent 的答案。
7. 关闭完成线程并记录谁做了什么、使用了什么证据和哪些意见未采纳。

## 必须产出

- Agent 选择理由
- 独立工作包
- spawn 指令
- 并行/顺序图
- 汇总与冲突处理计划

## 门禁与停止条件

- 没有独立交付物不得创建角色
- 禁止多个 Agent 同时修改同一工作区
- 子 Agent 不得无界继续委派

## 记忆更新

将参与 Agent、工作包、结论状态和未解决分歧写入任务检查点。

## 通用执行约束

- 先读当前目录适用的 `AGENTS.md` / `AGENTS.override.md`。
- 只加载与任务相关的政策和记忆；避免把整个制度包塞入上下文。
- 对事实附文件、符号、测试、日志或正式决定证据；不把推断写成事实。
- 遵守单一写入者、最小权限、可逆优先、秘密最小化和不覆盖用户改动。
- 当范围、风险、目标环境或关键假设变化时，暂停并重新分类。

## 建议输出格式

```markdown
# 结论
# 已验证事实与证据
# 假设 / 未知 / 冲突
# 决策或建议
# 风险与审批点
# 验证结果
# Memory Delta
# 下一步
```
