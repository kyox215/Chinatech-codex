# architecture-review

## 目标

用证据评估现状、方案、边界、兼容性、运维和长期成本，并形成可追踪架构决定。

## 输入

- 代码库地图
- 业务与非功能需求
- 现有架构/ADR
- 依赖、部署和运行约束

## 执行流程

1. 先描述当前架构事实：入口、模块、调用链、数据流、信任边界和部署单元，并引用文件。
2. 列出必须满足的质量属性：可靠性、延迟、容量、可维护性、可观察性、安全和成本。
3. 提出至少两个合理选项（明显只有一个时说明原因），比较复杂度、迁移、风险和长期负担。
4. 定义模块职责、公开接口、错误模型、幂等、重试、超时、事务和一致性边界。
5. 评估依赖引入、版本兼容、供应链、锁定风险和弃用路径；新增生产依赖需要理由。
6. 设计渐进式迁移、功能开关、并行运行、监控和回滚；避免一次性 Big Bang。
7. 需要长期约束时创建 ADR，包含状态、决定、理由、替代方案、后果和复审条件。

## 必须产出

- 架构事实图
- 方案比较
- 推荐方案
- 接口与质量属性
- 迁移/回滚方案
- ADR 草案

## 门禁与停止条件

- 不得只凭目录名称推断架构
- 方案必须覆盖失败模式和运维
- 重大决定没有 owner/复审条件不得标记 approved

## 记忆更新

更新架构部门记忆、ADR/DECISION_INDEX，并在任务中引用证据。

## 通用执行约束

- 先读当前目录适用的 `AGENTS.md` / `AGENTS.override.md`。
- 只加载与任务相关的政策和记忆；避免把整个制度包塞入上下文。
- 对事实附文件、符号、测试、日志或正式决定证据；不把推断写成事实。
- 遵守单一写入者、最小权限、可逆优先、秘密最小化和不覆盖用户改动。
- 当范围、风险、目标环境或关键假设变化时，暂停并重新分类。

## 建议输出格式

```markdown
# 结论
# 已验证事实与证据
# 假设 / 未知 / 冲突
# 决策或建议
# 风险与审批点
# 验证结果
# Memory Delta
# 下一步
```
