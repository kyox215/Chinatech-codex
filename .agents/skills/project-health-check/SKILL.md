# project-health-check

## 目标

从产品、架构、代码、数据、安全、质量、运行、文档和记忆多个维度建立真实基线。

## 输入

- 仓库与配置
- 项目记忆
- 测试/CI/部署
- 依赖、schema、权限和运行资料

## 执行流程

1. 先建立项目地图：入口、模块、依赖、数据、API、身份、部署、外部服务和文档。
2. 按领域并行只读审查，要求每个发现包含证据、影响、发生条件和推荐行动。
3. 检查产品流程完整性、架构边界、重复/死代码、类型与错误处理、数据约束和迁移历史。
4. 检查认证授权、秘密、依赖风险、测试覆盖与可信度、CI/CD、监控、备份、恢复和事故准备。
5. 检查文档/记忆漂移、无 owner 决定、陈旧 SOP、能力和权限不一致。
6. 按 P0（立即阻断/高危）、P1（重要）、P2（改进）排序，并考虑修复成本和依赖。
7. 输出 30/60/90 天路线图和第一批小而可验证的任务；未经批准不进行大规模重构。

## 必须产出

- 项目地图
- P0/P1/P2 发现
- 证据与影响
- 技术债/风险登记
- 分阶段路线图

## 门禁与停止条件

- 不得把风格偏好列为 P0
- 扫描工具结果需人工/Agent 复核
- 体检阶段默认只读

## 记忆更新

建立或更新 PROJECT_MEMORY、风险登记、技术债和审计日期。

## 通用执行约束

- 先读当前目录适用的 `AGENTS.md` / `AGENTS.override.md`。
- 只加载与任务相关的政策和记忆；避免把整个制度包塞入上下文。
- 对事实附文件、符号、测试、日志或正式决定证据；不把推断写成事实。
- 遵守单一写入者、最小权限、可逆优先、秘密最小化和不覆盖用户改动。
- 当范围、风险、目标环境或关键假设变化时，暂停并重新分类。

## 建议输出格式

```markdown
# 结论
# 已验证事实与证据
# 假设 / 未知 / 冲突
# 决策或建议
# 风险与审批点
# 验证结果
# Memory Delta
# 下一步
```
