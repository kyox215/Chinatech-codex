# ui-ux-review

## 目标

让用户体验在桌面、移动端、加载、空、错误和权限状态下保持一致，并可由前端和 QA 验证。

## 输入

- PRD/用户流程
- 设计系统与现有组件
- 目标设备与可访问性要求
- 真实数据形态和权限

## 执行流程

1. 确认页面任务、主要用户、首要动作和信息层级；删除无业务价值的装饰和重复信息。
2. 复用现有设计 Token 和组件，定义新增组件的职责、变体、尺寸、状态和键盘行为。
3. 覆盖默认、加载、骨架、空、错误、无权限、离线、部分成功、长内容和极端数据状态。
4. 设计移动端优先的布局变化，而不是简单缩小桌面表格；定义断点下的导航和操作优先级。
5. 检查可访问性：语义、标签、焦点、键盘、错误提示、颜色非唯一编码和动态内容公告。
6. 对删除、退款、取消、覆盖、批量等危险动作定义确认、影响预览、撤销或恢复。
7. 把交互说明映射到组件、数据需求、埋点和 UI 验收步骤。

## 必须产出

- 页面/组件结构
- 交互与状态表
- 响应式规则
- 可访问性要求
- UI 验收清单

## 门禁与停止条件

- 不得只交付正常截图状态
- 无权限与错误不能泄露敏感信息
- 危险操作必须体现后果和恢复路径

## 记忆更新

稳定设计模式进入 design/frontend 部门记忆；任务特定画面保留在任务文档。

## 通用执行约束

- 先读当前目录适用的 `AGENTS.md` / `AGENTS.override.md`。
- 只加载与任务相关的政策和记忆；避免把整个制度包塞入上下文。
- 对事实附文件、符号、测试、日志或正式决定证据；不把推断写成事实。
- 遵守单一写入者、最小权限、可逆优先、秘密最小化和不覆盖用户改动。
- 当范围、风险、目标环境或关键假设变化时，暂停并重新分类。

## 建议输出格式

```markdown
# 结论
# 已验证事实与证据
# 假设 / 未知 / 冲突
# 决策或建议
# 风险与审批点
# 验证结果
# Memory Delta
# 下一步
```
