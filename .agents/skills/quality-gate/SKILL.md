# quality-gate

## 目标

以独立证据决定是否完成，而不是根据实施者自述、代码外观或单一 happy path。

## 输入

- 验收标准
- 代码 diff
- 测试计划与结果
- 环境、数据和已知风险

## 执行流程

1. 建立验收标准到测试/证据的一一映射，标记自动、人工、静态、运行时和未覆盖。
2. 先验证核心正向流程，再覆盖无效输入、边界值、重复、并发、超时、失败、恢复和部分成功。
3. 验证角色和对象级权限、租户隔离、错误信息、审计记录和数据一致性。
4. 按影响范围运行单元、集成、端到端、迁移和回归检查；不要用全部测试掩盖关键测试缺失。
5. 审查测试可靠性：数据隔离、时区、随机性、外部依赖、重试和 flaky 结果。
6. 记录命令、环境、提交/工作区版本、结果、失败输出摘要和证据路径。
7. 结论只能是 PASS、CONDITIONAL 或 FAIL；Conditional 必须包含例外、风险接受人和期限。

## 必须产出

- 测试矩阵
- 实际执行证据
- 缺口和回归风险
- 质量门禁结论
- 复现步骤

## 门禁与停止条件

- 测试文件存在不等于执行通过
- 未覆盖的高风险验收标准不得 PASS
- 不能删除失败测试来获得绿色结果

## 记忆更新

写入 EVIDENCE、CHECKPOINTS；可复用测试约定进入 qa 部门记忆。

## 通用执行约束

- 先读当前目录适用的 `AGENTS.md` / `AGENTS.override.md`。
- 只加载与任务相关的政策和记忆；避免把整个制度包塞入上下文。
- 对事实附文件、符号、测试、日志或正式决定证据；不把推断写成事实。
- 遵守单一写入者、最小权限、可逆优先、秘密最小化和不覆盖用户改动。
- 当范围、风险、目标环境或关键假设变化时，暂停并重新分类。

## 建议输出格式

```markdown
# 结论
# 已验证事实与证据
# 假设 / 未知 / 冲突
# 决策或建议
# 风险与审批点
# 验证结果
# Memory Delta
# 下一步
```
