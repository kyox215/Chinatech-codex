# product-requirements

## 目标

把老板意图转成明确的用户、场景、业务规则、状态流转、异常行为和优先级，避免技术先行定义产品。

## 输入

- 业务目标
- 用户和角色
- 当前流程/状态机
- 客服、运营、销售或合规限制

## 执行流程

1. 定义目标用户、使用场景、痛点、预期结果和非目标；量化成功指标或至少定义观察信号。
2. 描述主流程、替代流程、失败流程、取消/重试/超时、重复提交和并发行为。
3. 建立角色权限矩阵，区分“看见”“创建”“修改”“批准”“取消”“导出”和“管理”。
4. 定义业务状态、合法转换、触发者、前置条件、副作用、通知、审计字段和终态。
5. 明确字段含义、校验、默认值、可编辑时机、国际化/时区/金额精度等边界。
6. 按 Must/Should/Could/Later 排优先级，避免把未来扩展全部塞进当前版本。
7. 将每条规则转化为 Given/When/Then 验收标准，并与现有行为的兼容策略对齐。

## 必须产出

- 轻量或完整 PRD
- 用户流程
- 角色权限矩阵
- 状态机
- 业务规则和验收标准

## 门禁与停止条件

- 前端隐藏不是权限控制
- 状态转换必须由服务端验证
- 未定义异常和重复操作的流程不完整

## 记忆更新

稳定业务规则进入产品部门记忆；当前任务细节保留在 TASK/PRD。

## 通用执行约束

- 先读当前目录适用的 `AGENTS.md` / `AGENTS.override.md`。
- 只加载与任务相关的政策和记忆；避免把整个制度包塞入上下文。
- 对事实附文件、符号、测试、日志或正式决定证据；不把推断写成事实。
- 遵守单一写入者、最小权限、可逆优先、秘密最小化和不覆盖用户改动。
- 当范围、风险、目标环境或关键假设变化时，暂停并重新分类。

## 建议输出格式

```markdown
# 结论
# 已验证事实与证据
# 假设 / 未知 / 冲突
# 决策或建议
# 风险与审批点
# 验证结果
# Memory Delta
# 下一步
```
