# 工单配件采购

状态板入口改为配件采购表格：按工单分组，每个采购配件独立记录供应商、采购单价（EUR）、数量和进度。已有列表/卡片保持不变。

## 业务边界

- 采购行独立于维修报价行；可引用同工单报价项目，也可填写自定义配件。旧工单无 line_id 时也可添加。
- 待下单允许成本留空，空值不变成零；下单前必须具备供应商和单价。明确输入0属于有效零成本。
- 保存并下单是一次原子操作；到货仅由已下单进入。已到货行在本入口只读。
- 勾选当前已加载工单的配件，批量设供应商、标记下单或到货。设供应商不改变各项成本/数量；状态不一致时UI提示重新选择。服务端逐项返回成功或失败，失败项保留选择，不能把部分成功显示成全成功。
- 记录仅用于工单采购跟进。不会增加库存、创建采购入库批次、分配库存、改变客户报价/付款、发送客户通知或向供应商发送真实订单。采购支出不自动重复计入历史成本账本。

## 权限与数据

独立 `REPAIRDESK_ORDER_PURCHASING_ENABLED=1` 控制此功能；不会开启已退役内部成本或库存采购开关。读接口要求工单读取、finance:cost_manage及supplier:read；写接口要求工单维修编辑及finance:cost_manage，设置供应商还需supplier:assign。沿用服务端当前会员权限，不新增角色默认授权。

`order_part_purchases` 单独保存敏感采购成本。普通工单列表、fault_prices、客户状态页和实时广播不含采购成本。客户端仅调用既有RepairDesk BFF；数据库RPC复核店铺、权限、对象、版本及幂等键。

工单辅助parts_status由新采购记录聚合（有待下单→needed；否则有已下单→ordered；全部到货→arrived），主维修状态、付款和通知状态不改。没有新采购行的旧工单不回填、不改状态。事务更新工单版本，复用orders域跨设备失效；编辑器冻结打开时版本，冲突保留草稿。

## 响应式与交互

手机采用四个物理列（勾选、配件/数量、供应商/单价、进度/操作），三组业务信息无横向滚动。iPad与桌面复用数据和操作合同，44px触控目标。采购编辑复用现有Dialog、MoneyKeypadInput和脏草稿关闭保护；zh-CN/en/it-IT。

## 数据库回归验证

仅在隔离 PostgreSQL 17 测试库依次执行 `supabase/test-fixtures/order-purchasing-schema.sql`、本功能迁移及 `supabase/test-fixtures/order-purchasing.sql`。夹具覆盖撤权重放、审计失败回滚、供应商权限、版本冲突和无库存副作用。

本地 Docker 测试库还可运行 `python3 supabase/test-fixtures/order-purchasing-concurrency.py <测试库名> <测试容器名>`；它使用夹具专用账号、已知测试密码及临时触发器，不能用于生产数据库。验证单条与批量交错、同工单多配件并发聚合、多工单相反输入顺序。所有采购写入先按工单ID顺序持有父记录锁，再更新配件；最小操作审计与采购修改同事务提交。
