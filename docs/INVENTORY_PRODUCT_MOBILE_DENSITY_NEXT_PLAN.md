# 商品库存移动端高密度完善计划

Status: implementation candidate
Task: `TASK-20260731-003-inventory-product-mobile-density`
Owner: Product + UX + Frontend + QA / Integration Lead
Last reviewed: 2026-07-31 CEST

## 1. 目标

在不改数据库、库存 API、权限模型和商品/回收边界的前提下，把商品库存的列表、快速录入、详情和编辑统一成适合门店单手操作的高密度工作区：关键内容一目了然，390px 手机尽量在首屏或单页内完成，且不以隐藏业务数据、缩小触控区或牺牲可访问性换取密度。

本阶段只完善商品库存。回收估价、采购、调拨、盘点、批量操作、库存生命周期动作和跨设备编辑冲突协议属于后续独立阶段。

## 2. 已确认的产品边界

- 商品库存与回收保持独立路由、DTO、查询键和实时失效边界。
- 列表和详情只返回脱敏设备标识；完整标识只在具备 `inventory:update` 权限的编辑入口短时显示。
- 不新增数据库迁移、RPC、API 字段、权限、依赖、环境变量或生产数据操作。
- 保持既有商品创建、编辑、幂等、CAS、成本权限和设备标识唯一性语义。
- 兼容历史详情响应缺少 `identifiers` 数组的情况，UI 边界按空数组处理。
- 页面不伪造电池健康、锁状态、质检或库存动作，也不加入未接线按钮。

## 3. 信息架构

### 3.1 商品列表 `/inventory`

手机端每个商品使用三段式高密度卡：

1. 左侧 36px 类别图形，快速识别设备类型。
2. 中间三行依次显示品牌型号、SKU、脱敏主标识或库位。
3. 右侧显示状态和售价，金额使用统一 `MoneyText`。

目标卡片高度为 `84–88px`，卡片间距 `6px`。390px 视口在标准标题、搜索与筛选区域下应能看到至少第六件商品的内容，不依赖横向滚动。桌面端继续使用六列高密度表格，行高约 `52px`。

列表查询必须同时满足：已选门店、`inventory:read` 权限、商品库存 UI 旗标开启。筛选或分页变化保留上一批列表，避免空白闪烁；加载、空、错误、无权限和关闭态分别呈现。

### 3.2 快速录入 `/inventory/new`

首屏顺序固定为：

1. 类别：手机、平板、电脑、游戏机、其他，390px 固定五列，每项至少 `44px` 高。
2. 品牌与型号：手机端同一行两列，长值截断但可完整编辑。
3. 常用规格：容量、RAM、颜色采用两列高密度网格。
4. 主设备标识：保持扫码、照片本地识别、粘贴和手输能力。
5. 更多信息：低频规格和经营字段按需展开。
6. 底部固定双动作：“保存商品”和“保存并继续录入”。

页面加载门店/权限期间只显示骨架，不短暂暴露可编辑表单。真实输入字号至少 `16px`，固定动作区考虑 safe area，按钮触控高度至少 `44px`。

### 3.3 商品详情 `/inventory/[id]`

详情遵循 RepairOS Floating Card，并将 430px 手机宽度作为内容上限：

- 首卡只显示类别图形、品牌型号、SKU、状态、售价、有权限的成本和库位。
- 主标识不在首卡重复，避免同一脱敏标识在一页出现两次。
- 设备工作台使用三列紧凑资料格；六项资料在两行内完成。
- 设备身份集中显示脱敏 IMEI、序列号、EID 和 EAN/GTIN。
- 更新时间作为首卡次级元数据；备注仅在有值时显示。
- 核心详情在 430px 标准样本中尽量单页可见，不嵌套第二个正文滚动容器。

### 3.4 商品编辑 `/inventory/[id]/edit`

- 查询必须同时满足门店、`inventory:read`、`inventory:update` 和商品库存 UI 旗标。
- 无更新权限时先显示权限结果，不进入永久加载态，也不请求完整编辑资料。
- 品牌、型号和 GTIN 使用字段级错误关联，表单采用自有校验而非浏览器原生气泡。
- 主要字段使用两列紧凑网格，底部固定“取消 / 保存修改”双动作。
- 本阶段保留现有版本冲突行为；字段级安全合并协议另立 R3 任务，不在 UI 密度改造中扩张。

## 4. 响应式规格

| 视口 | 列表 | 新建/编辑 | 详情 |
| --- | --- | --- | --- |
| `390px` | 84–88px 卡片，三段式 | 五列类别、核心字段双列、固定双动作 | 最大宽度 430px、三列资料格 |
| `430px` | 同手机规则，增加文字余量 | 同手机规则 | 核心样本尽量一页呈现 |
| `768–1023px` | 双列卡片或紧凑列表 | 双列工作区 | 放宽后的 Floating Card 工作区 |
| `>=1024px` | 六列桌面表格，约 52px 行高 | 桌面表单工作区 | 桌面详情工作台 |

所有常用视口必须满足：

```txt
document.documentElement.scrollWidth <= window.innerWidth
```

移动端按钮/链接/类别选项触控区域至少 `44px`；输入、选择器和文本域字号至少 `16px`；状态使用语义 badge，金额使用共享金额组件，不新增硬编码颜色。

## 5. 页面状态与访问控制

每个入口至少覆盖以下状态：

- shell/权限加载：骨架，不展示可编辑内容。
- 功能关闭：解释性关闭态，不发业务查询。
- 无门店：门店选择或无门店提示。
- 无读取权限：不请求列表/详情数据。
- 无更新权限：详情可读但编辑入口关闭；编辑页不请求完整标识。
- 查询加载：保留尺寸稳定的骨架或上一页结果。
- 空结果：显示清晰空态与可用主动作。
- 错误：显示可重试错误，不泄露服务端细节。
- 提交中：禁用重复提交；成功后按既有查询键失效。
- 字段错误：错误文字通过 `aria-invalid` 与 `aria-describedby` 关联。

## 6. 数据、安全与隐私

- 本阶段无 schema、migration、RPC、repository、permission 或 retention 变化。
- 列表、普通详情、日志、toast、截图和测试数据不得出现完整 IMEI、序列号或 EID。
- 编辑数据仍由既有服务端权限和审计保护；客户端门禁只用于避免不必要请求，不代替服务端授权。
- 查询保留上一页结果只发生在同一 React Query 权限/租户根内；门店、membership 或权限变化仍按既有规则清理缓存。
- 截图使用合成数据和脱敏标识，不包含真实客户资料或生产凭据。

## 7. 验收合同

### 自动化

- ESLint、TypeScript、全量 Vitest 和 production build 通过。
- 单元测试验证：旗标关闭不请求列表、无更新权限不请求编辑资料、shell 加载不闪现表单、缺失 `identifiers` 的旧响应可渲染。
- Playwright 覆盖 Chromium 与 WebKit：
  - 390px 列表卡片高度 `84–88px`，第六件商品在视口内可见。
  - 390px 录入五个类别全部可见、触控高度至少 `44px`、固定动作可见、输入 `16px`。
  - 430px 详情核心工作台一页清楚呈现，脱敏主标识只出现一次。
  - 390px 编辑字段错误与固定动作正常。
  - 1024px 列表为六列桌面布局。
  - 所有场景无页面级横向溢出。

### 人工视觉

- 列表能快速扫出类别、商品、SKU/标识、状态和售价。
- 录入首屏无步骤条和横向类别滚动，主动作不遮挡字段。
- 详情无重复标识、无伪造资料、无大面积无效留白。
- 编辑错误能直接定位到字段，键盘弹出时不触发页面缩放。

## 8. 发布计划

1. 基于最后安全库存/回收业务树恢复库存功能，并重放当前生产订单修复。
2. 完成 UI、测试、文档和任务记忆；独立 QA 只读复核。
3. 运行 lint、typecheck、test、build、Chromium/WebKit 回归与生产模式截图。
4. 获取项目集成租约，重新确认远端 `main` 与当前生产部署。
5. 非强制推送任务分支，创建可验证预览；通过后以包含远端 `main` 的快进历史推送生产分支。
6. 验证 Vercel 部署状态、精确 Git SHA、构建日志和只读生产入口，不创建生产商品。

本阶段不执行 Supabase migration、数据回填或真实库存写入。生产异常时先回滚 Web 到组合基线提交 `b6332f8c`（安全库存树 + 当前生产订单修复），不删除库存数据；后续以向前修复为主。
