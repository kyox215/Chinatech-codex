## 1. 结论与阅读方式

“目录很脏”和“加载时很脏”都有实际证据，但原因不同。

- 工作区主要是**未提交成果、历史副本、截图、缓存、任务登记混在一个长期运行的目录中**。不能用一次 `git clean` 解决。
- 骨架屏主要是**继续描绘旧页面结构**：iPad 加载时单列、完成后双列；客户页出现实际页面没有的统计卡；详情占位宽度和分区与真实页面不一致。应先修结构，再减弱颜色和动画。
- 业务代码的单元测试基础较强，但**浏览器测试的环境合同和部分断言已经漂移**。单元测试全绿不能替代完整业务验收。
- 本轮没有获得真实隔离数据库及普通角色账户，因此没有把模拟保存、合成收款或 UI 能力开关验证当作真实后台/RLS/账务验证。

以下列出 **45 个去重的整改或待核实点**。它们包含已复现问题、工程风险、配置缺口及设计建议，**不是 45 个已证实的线上故障**。同一个问题在不同语言或宽度下重复出现，不重复计数。本轮没有足够证据判定 P0。

证据等级：**A**＝本轮浏览器/命令复现；**B**＝源码或配置直接证据；**C**＝待测影响或设计建议。P1 表示优先处理的重要问题，P2 表示后续改进；P1 并不自动等于线上发布阻断。

优先读：UI-01、UI-04、UI-06、UI-10、QA-01、QA-04、WS-01、WS-03，以及第 6 节正确业务流程。

## 3. 工作区与工程组织：WS-01—WS-20

<a id="ws-01"></a>

### WS-01｜未提交业务成果与历史资料混在同一长期工作区（P1 / A）

**证据与触发：** `git-status-before.txt` 中 76 个修改条目跨客户、订单、实时同步、UI、测试和文档，未跟踪资料还包括迁移与任务记录。直接整目录提交、清理或重置时会把不同任务混合。**建议：** 按当前任务、历史候选、正式文档、可再生产物建立归属清单；先保存文件哈希及可恢复补丁，再决定分批集成。**验收：** 每批文件都有明确用途和任务归属；未知归属保留原位，不能以“未跟踪”为删除依据。

### WS-02｜README 的“最新状态”实际是历史快照（P1 / B）

**证据：** [README](../README.md) 第 40—52 行把 9 月 10 日任务称为最新，但当前已有更晚任务和大量修改；README 自身尚未跟踪。**影响：** 接手者可能把未发布候选误当作当前权威版本。**建议：** 保留历史说明，但移出当前入口；首页只描述稳定项目地图，状态链接到核验过的当前任务。**验收：** README 不再用过期任务推断当前发布/工作区状态。

<a id="ws-03"></a>

### WS-03｜工作树登记积累了大量失效项（P1 / A）

**证据：** worktrees.txt（本地证据：`../artifacts/workspace-loading-audit-20260925/evidence/worktrees.txt`）：202 条登记中 179 条 prunable。**影响：** 判断哪个目录可用、哪个分支仍有独有成果变难。**建议：** 先核对 path 是否存在、锁定状态、分支/独有提交和引用，再制作 prune dry-run 清单；仅清登记与删除目录分开执行。**验收：** 所有保留分支、恢复引用和实际目录仍可访问；不把 prunable 当作“可以删分支”。

### WS-04｜`work/` 本地副本没有明确的 Git 排除边界（P1 / A+B）

**证据：** 约 7.8 GiB 的 `work/` 出现在 `?? work/`，而 `.gitignore` 未排除它；其中包含多个带项目入口的副本。**影响：** `git add .` 或人工启动服务容易带入错误版本。**建议：** 在核对需要版本化的少量文件后，统一为本地工作副本区域并排除；不要把应提交的文档一并藏掉。**验收：** 日常状态只显示真正待提交成果，旧副本仍有来源和恢复说明。

<a id="ws-05"></a>

### WS-05｜缓存已经成为明显的磁盘占用来源（P2 / A）

**证据：** 只读统计时 `.next/` 约 11 GiB，主要在 `.next/dev/`。**影响：** 占用空间，也容易使人工误以为源码本身巨大。**建议：** 将缓存清理纳入“确认进程归属→停止本项目对应服务→删除可再生缓存→重建验证”的独立步骤。**验收：** 重建可成功且无其他服务受影响；本轮未清理正在使用的缓存。

## 5. 测试、环境及交付流程：QA-01—QA-14

<a id="qa-01"></a>

### QA-01｜开发预览 manifest 500 污染 WebKit 回归（P1 / A+B）

**证据：** 开发服务器请求 `/manifest.webmanifest` 报 `cookies was called outside a request scope`，调用链 `manifest.ts:6 → shared/i18n/server.ts:8`。三语言直接请求均 500；相同源码的本地生产构建三语言均 200。**整改：** 在开发和构建后都覆盖 manifest 请求，调整其语言取得方式与框架运行上下文的兼容性。**验收：** 两种模式下均 200、内容合法、三语言正确，不能只过滤浏览器 console 错误。**边界：** 本轮不足以判定线上 PWA 损坏。

<a id="qa-02"></a>

### QA-02｜默认 mock 启动不等于完整库存测试环境（P1 / A+B）

**证据：** 首轮 11 个库存创建用例被缺少页面能力/入口阻断；默认 mock 的 store permissions 缺 `inventoryProductsUiEnabled` 等能力。仅在临时用例补齐明确的模拟能力后，390 入口及 mock 创建跳转通过。**整改：** 测试入口应声明功能、角色及响应合同，并在跑浏览器前检查 bootstrap；不要靠测试中途等待一个永远不会出现的按钮。**验收：** 环境不足时立即报告具体能力缺失；完整 fixture 的库存流程可稳定执行。补验不是对真实库存权限的验证。

<a id="qa-03"></a>

### QA-03｜回收写入暂停与测试/页面可操作状态不同步（P1 / A+B）

**证据：** `transparent-quote-policy.ts` 要求 `REPAIRDESK_BUYBACK_TRANSPARENT_QUOTE_WRITE_ENABLED=1`；默认预览没有该条件，报价创建返回 403，而用例仍按可写流程提交。**影响：** 多宽度失败共享一个环境根因；用户也可能填完才知道功能暂停。**整改：** 将只读/暂停能力传给页面，提前说明原因；测试分为“暂停时拒绝”和“隔离可写 fixture”两组。**验收：** 不通过打开真实生产写开关修测试；两种状态各自有明确预期。

<a id="qa-04"></a>

### QA-04｜草稿稳定性用例依赖脆弱的页面级探针（P1 / A+B）

**证据：** 390 用例读取 `window.__newOrderStability.draftReads` 时对象不存在；820/1440 用例各超时 180 秒。原用例通过 history.replaceState 操作场景，并把 React/DOM 状态挂在页面全局。**结论：** 稳定性验收没有通过，尚不能仅凭探针异常判断真实草稿丢失。**整改：** 先定位是否发生意外导航/探针丢失，再优先用可见输入、草稿存储和明确保存结果验证；需要内部探针时记录生命周期。**验收：** 输入、取消、重开、刷新、旋转、自动保存连续执行且数据一致，不只是让对象不报 undefined。

<a id="qa-05"></a>

### QA-05｜报价测试用固定 Save 名称寻找已变为 Saving 的按钮（P2 / A+B）

**证据：** 1440 英文报价失败发生在请求 pending 时 `getByRole(...name:'Save')`；实际组件 `order-detail-screen.tsx:2429` 会切换为 saving 文案。其余 17 个报价场景通过。**整改：** 以稳定容器或控制标识定位，再分别检查 pending 文案与 disabled；保留重复点击、失败重试和草稿保留断言。**验收：** 受控未完成请求时仍能证明按钮禁用，恢复后可重试。不能把这个定位失败直接归类成金额错误。

<a id="qa-06"></a>

### QA-06｜离线队列断言仍使用旧名称（P2 / A+B）

**证据：** 两个引擎都期望 aria-label 含“全部状态”，实际为“当前队列”，控件已经 disabled。**整改：** 根据当前业务队列语义更新用例，同时继续验证离线保留旧数据、禁止错误切换和联网恢复。**验收：** 断言检查行为及可访问名称，而不是保留过时文案以制造绿色结果。

<a id="qa-07"></a>

### QA-07｜部分浏览器测试把结果写入历史任务目录（P1 / B）

**证据：** inventory-create、product-sales 等 spec 使用固定的 `artifacts/TASK-20260912-002-ui-consistency-framework/fullscreen-run3/...`，不是当前 testInfo 输出目录。**影响：** 新执行可能覆盖旧证据，文件时间和历史报告含义失真。**整改：** 所有测试产物写到唯一 run 目录，再由当前报告链接；本轮在临时副本运行，未覆盖仓库历史任务产物。**验收：** 连跑两次不互相覆盖，原截图哈希不变。

### QA-08｜失败 trace 配置与重试次数不匹配（P2 / B）

<a id="qa-09"></a>

### QA-09｜基础 smoke 把登录页也算作业务路由成功（P2 / B）

### QA-11｜本地综合 check 与 CI 的规则检查不一致（P2 / B）

<a id="qa-12"></a>

### QA-12｜测试数量没有对应关键风险的覆盖率证据（P2 / B+C）

### QA-13｜骨架测试没有约束它与真实布局的一致性（P2 / B）

<a id="qa-14"></a>

### QA-14｜当前隔离环境不足以证明完整真实业务闭环（P1 / A，验证缺口）

**证据：** 当前根目录只有 `.env.example`；本轮明确使用内存 mock 和 HTTP fixtures。合成创建立即刷新成功，但后续尝试继续编辑新 ID 时详情读取失败；没有可靠数据库可核对持久记录。**结论：** 不据此判定生产数据丢失，也不声称真实流程已完全跑通。**整改：** 准备项目专属测试门店、Owner/Manager/Technician/Viewer 账户、固定种子及重置合同，完成真实后台闭环。**验收：** 同一测试工单跨刷新、跨会话、跨角色仍一致；付款/库存/审计可由测试后台读回。不要借用生产客户做这项验证。

## 6. 正确的业务操作与验收流程

这部分是后续跑通业务时的检查顺序，沿用 [工单生命周期与客户财务标准](ORDER_LIFECYCLE_CORRECTION_STANDARD.md)、[数据一致性声明](REALTIME_DATA_CONSISTENCY_DECLARATION.md) 和 [启动与打印声明](STARTUP_PERFORMANCE_AND_PRINT_READINESS_DECLARATION.md)。它不新增状态规则，也不授权生产写入。

### 6.1 一张维修工单如何走完

| 顺序 | 正确操作 | 必须核对的结果 | 常见错误做法 |
|---|---|---|---|
| 1. 环境与身份 | 确认测试站点、门店、操作者角色和已启用功能 | 门店名、权限、数据源一致 | 看到页面就假定连的是测试库 |
| 2. 查找客户 | 按电话检索，核对同号候选，必要时明确选择新增 | 已有客户不重复建；共享号码能明确区分 | 修改客户选择时暗中重绑既有工单 |
| 3. 录入设备 | 品牌、型号、有效标识、保管状态、随附物品按当前表单填写 | 设备记录与客户/工单关联一致 | 把 IMEI、SN、EAN 混为一个识别规则 |
| 4. 记录故障 | 记录客户描述；检测结论后补 | 描述与诊断分别可追溯 | 为了保存随意填一个诊断结果 |
| 5. 建单 | 在当前页面的新建工作区提交一次 | 明确成功 ID；无照片不要误报上传；失败保留输入 | 点击无响应时反复新增 |
| 6. 重新读取 | 打开详情、刷新，再从列表/客户历史找到同一单 | 客户、设备、状态、保管状态一致 | 只看到成功 toast 就宣布完成 |
| 7. 检测与报价 | 通过报价编辑器录项目和金额；接单时允许暂不报价 | 空金额不自动变 0，合计正确，取消可恢复 | 把报价草稿当正式客户同意 |
| 8. 正式确认 | 按现有报价发布/客户确认流程操作 | 待确认、同意、拒绝有明确事实依据 | 仅改显示标签伪造客户确认 |
| 9. 维修与配件 | 按可用状态动作推进；涉及配件时核对关联 | 状态、负责人和设备保管分别正确 | 把“维修完成”误当成“已交付” |
| 10. 收款 | 使用专门收款动作，核对金额、方式、余额和回执 | 收款事实由账本派生；重复提交不重复入账 | 修改报价或初始定金来代替真实收款 |
| 11. 通知与交付 | 在授权范围内通知；确认设备实际交接 | 通知事实、维修状态、付款状态各自清楚 | 默认自动给真实客户发消息 |
| 12. 结案检查 | 列表、详情、客户历史、统计和收据互相核对 | 已交付但待收可按现有规则正确表达 | 强行把所有完成工单都改成已结清 |
| 13. 异常处理 | 取消、退机、更正、重开走各自专用入口 | 权限、原因、版本、审计记录和退款边界保留 | 删除记录来掩盖错误金额或历史 |

财务上尤其要保持三点：**累计订单额不是已收收入；取消时余额不算当前待收；无财务权限不是显示 €0.00**。已完成工单仍可能有合法待收款，不能为简化界面改变这个规则。

### 6.2 “新增信息”应怎样被验证

对客户、设备、故障、备注、报价、随附物品和照片，每次新增/编辑至少走：

1. 打开编辑入口，确认当前实体和现有值。
2. 输入新值，验证空值、格式、长文本和必填提示。
3. 先取消一次，确认原值没有被偷偷修改。
4. 再次编辑并保存，确认按钮忙碌、禁止重复提交且错误可理解。
5. 关闭、重开并刷新，确认读回的是已保存值。
6. 检查相关列表、客户历史或统计是否同步。
7. 用另一测试角色读取；需要限制的数据不应因刷新或错误提示泄露。
8. 注入一次失败或版本冲突，确认草稿保留、可以恢复，不能覆盖别人刚保存的修改。

照片还需单独验证：零照片、有照片、部分成功、不确定提交、重试、离开确认。文件不能只在浏览器列表里出现就算后台上传成功。

### 6.3 库存与销售应另跑一条闭环

商品录入 → 类别与标识校验 → 入库后读回 → 查看/编辑 → 预留或销售 → 定金/补款 → 实际交付 → 收据/质保 → 必要的售后入口。

每一步检查商品身份、数量、状态和权限；成本与售价分开，不能在无成本权限时通过前端隐藏代替服务端授权。商品售卖的模拟 UI 用例已覆盖定金、补款、交付和历史收据，但本轮没有真实库存/账本事务证据。

- 一个用例失败先定位；同根因不反复跑整套矩阵，不用放松断言换取通过。
