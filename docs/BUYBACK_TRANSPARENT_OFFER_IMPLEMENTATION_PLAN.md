# Chinatech 回收管理：透明协商报价实施计划

状态：已选定、进入实施
任务：`TASK-20260730-014-transparent-buyback-offer-implementation`
目标环境：Chinatech RepairDesk 生产 `/buyback`

## 1. 最终产品形态

透明协商报价不是一张装饰性报价卡，而是前台与客户面对面解释价格、记录答复的正式工作台。

```text
回收记录列表
  → 打开一台设备
  → 同屏查看初估、检测发现、逐项扣减和最终报价
  → 选择客户答复：接受 / 考虑中 / 拒绝
  → 保存报价记录
```

本版本只完成“报价与检测记录”。付款、证件、签名、所有权转移、商品入库仍保持关闭。

## 2. 页面结构

### 回收列表

- 搜索、扫码、筛选和“新建报价”作为明确入口。
- 手机端使用紧凑记录卡；桌面使用无需横向滚动的自适应卡片/有限列结构。
- 每条记录突出：设备、报价性质、当前金额、客户答复、风险和唯一下一动作。
- 不出现商品详情、转入库存、售卖整备或步骤进度。

### 透明报价工作台

1. 设备摘要：型号、容量、颜色、电池、脱敏 IMEI。
2. 价格对照：初估区间、系统建议、人工最终报价、差额、有效期。
3. 报价依据：市场参考、外观、功能、电池、维修/整备预留和人工调整理由。
4. 检测摘要：只突出异常和未检项；正常项折叠为计数。
5. 客户答复：接受、考虑中、拒绝，并提供一个“保存客户现场口头答复”主动作。
6. 安全说明：答复不等于付款、签名、收购完成或商品入库。

## 3. 价格语义

| 名称 | 含义 | 可否承诺成交 |
|---|---|---|
| 初估区间 | 根据型号与客户自述生成的参考范围 | 否 |
| 系统建议价 | 结合检测和扣减计算出的建议 | 否 |
| 人工最终报价 | 门店准备向客户提出的当前报价 | 仅作为报价，不等于成交 |
| 成交价 | 完成合规交接、签署与付款后的金额 | 本版本不启用 |

所有减价必须显示原因。人工最终报价偏离系统建议时必须填写原因，不能只改数字。

## 4. 客户答复状态

| 答复 | 保存行为 | 禁止行为 |
|---|---|---|
| 接受 | 保存为 `accepted`，记录当前报价和检测依据 | 不付款、不签名、不转库存 |
| 考虑中 | 保存为 `deferred`，保留有效期和后续联系状态 | 不自动接受、不自动成交 |
| 拒绝 | 保存为 `rejected` 并关闭本次跟进，保留原因和历史记录 | 不删除记录、不扣留设备 |

重复点击时主动作进入 pending 并禁用；请求失败保留本页内容，允许重试，不能生成重复记录。

## 5. 手机与桌面

- `390/430px`：单列 Floating Card，主动作固定在内容底部并留安全区；输入字号至少 16px。
- `768px`：设备/价格摘要可双列，答复卡仍保持完整宽度。
- `1024/1440px`：左侧报价依据，右侧客户答复和安全提示；不使用宽表。
- 全断点：`scrollWidth <= innerWidth`，触控区至少 44px，无水平拖动选项。

## 6. 状态与异常

- Loading：结构等高 skeleton，不闪现旧报价。
- Empty：区分无记录与筛选无结果。
- Error：明确“不是空数据”，提供重试。
- Offline：可查看草稿，但禁止提交；恢复网络后用户主动保存。
- Conflict：服务端状态已变化时停止覆盖，提示刷新重开。
- Partial success：创建成功、后续状态更新失败时复用已创建 ID 重试。
- Success：只显示“报价答复已保存”，禁止显示“收购完成”。

## 7. 安全与隐私

- 普通页面只显示 IMEI/电话尾号，不把完整值写进 Toast、错误、截图或无障碍名称。
- Find My/激活锁、权属、MDM、标识不一致和危险电池继续作为风险阻断信息。
- quote-only 保存不上传证件、签名、设备私人内容或付款资料。
- 服务端继续执行店铺隔离、角色权限与状态转换校验；UI 隐藏不作为权限控制。

### 专用权限矩阵

| 能力 | Owner | Manager | Sales | Technician | Viewer |
|---|---:|---:|---:|---:|---:|
| 查看脱敏回收记录 | 是 | 是 | 是 | 是 | 否 |
| 创建初始报价 | 是 | 是 | 是 | 否 | 否 |
| 发布新报价版本 | 是 | 是 | 否 | 否 | 否 |
| 记录客户现场口头答复 | 是 | 是 | 是 | 否 | 否 |
| 付款、证件、签名、入库 | 关闭 | 关闭 | 关闭 | 关闭 | 关闭 |

### 数据与一致性合同

- `buyback_quote_revisions` 追加保存初始报价与每次改价，不覆盖旧版本。
- `buyback_quote_responses` 把接受、暂缓或拒绝绑定到精确报价版本。
- 专用原子 RPC 同一事务写入报价账本、当前投影、业务时间线和审计；任何一步失败均回滚。
- 更新使用 `expected_updated_at` 做 CAS；旧页面不能静默覆盖新报价。
- `idempotency_key` 对断网重试提供同载荷重放，不生成重复报价或答复。
- 通用库存创建/更新入口拒绝 `quote_payload`，报价只能经过专用权限和命令。
- 列表 DTO 在服务端只返回 IMEI/电话尾号；客户侧报价 DTO 不下发成本、利润、内部售价或计算公式。

## 9. 发布与回滚

- 发布前保存旧生产 deployment ID 和新提交 SHA。
- 先应用追加式报价账本迁移，再部署应用；应用发布前必须确认三条 RPC 仅授权 `service_role`，浏览器角色无表/RPC 访问权。
- 新构建先验证 `/buyback` 正常渲染、原子写入、quote-only 网络边界，再进入生产。
- 以下任一情况立即回滚：保存失败、跨店数据、完整 PII/IMEI 暴露、错误出现付款/签名/库存联动、页面 5xx 或移动端严重溢出。
- 第一止损始终是关闭 `REPAIRDESK_BUYBACK_TRANSPARENT_QUOTE_WRITE_ENABLED`，并保持当前构建中“通用 `quote_payload` 写入拒绝”护栏。
- 新账本一旦产生记录，不得直接恢复到缺少该护栏的旧 deployment，否则旧代码可能改写当前投影而不追加版本。UI 需要回退时，先发布“旧 UI + 新服务端护栏”的兼容构建。
- 新增表和 RPC 为追加式兼容结构，不在紧急回滚中删除；账本保留供审计和恢复。回滚 smoke 必须验证通用库存更新仍无法改写透明报价投影。
