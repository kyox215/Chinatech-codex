# 商品售卖日常工作流

适用版本：2026-09-26 候选。生产执行结果见本任务发布证据；本文描述实际操作和接口边界。

## 门店操作

| 时点        | 操作                                                                                     | 完成依据                                                           |
| ----------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 开门 / 接班 | 商品管理 → 日结与待办，检查待收款、付清待交付、缺凭证、待核验、异常和到期跟进            | 销售员工查看自己负责的订单；负责人查看全店                         |
| 接待顾客    | 商品详情 → 售卖 / 收定金，选择客户、确认售价与本次实收、收款方式、保修约定及是否当场交付 | 先核对交易，再确认；成功页显示销售单号、累计已收、余额和状态       |
| 留货        | 保存定金或付清留店记录；在销售跟进中指定负责人和下次跟进时间                             | 保修从实际交付开始；跟进时间按罗马时间显示到分钟                   |
| 补款 / 提货 | 在原销售单补收余额；付清后确认实际交付                                                   | 以系统成功结果为准。提交不确定时保留原表单重试，不另建销售单       |
| 收银开单    | 在现有收银系统开具商业凭证 / 发票；回到销售跟进关联类型、编号及开具时间                  | 系统仅保存关联信息，不替代财政设备或发票平台                       |
| 核验凭证    | owner / manager 对照外部单据，执行核验                                                   | 更正编号必须写原因，旧版本保留，更正后重新核验                     |
| 异常处理    | 记录收款差异、凭证问题、客户请求或交付问题；人工处理后登记依据和结果                     | 此操作不执行退款、退货入库、余额冲正或原付款修改                   |
| 交班 / 日结 | 选择罗马营业日期，核对成交额、实收和各收款方式；检查当前未结事项                         | 实收按付款发生日期；成交额按销售约定日期。历史日期不会回溯待办状态 |

跟进时间用于待办排序和到期提示，当前版本没有自动短信、微信、邮件或推送。完成一次跟进后，应清除到期时间或设置下一次时间，并补工作备注。不要在备注中填写银行卡、证件号码等敏感资料。

## 权限和统计

- 操作限已启用销售功能门店中的活跃 owner、manager、sales。服务端和数据库分别校验门店、成员及员工状态。
- 财政凭证核验限 owner / manager。财务汇总限 owner 或持有有效 `finance:aggregate_read` 授权的 manager；其他账号的 `finance` 为 null。
- sales 的日报待办只包含本人负责订单，以及本人创建且尚未分配的订单。owner / manager 可看全店待办。
- “当前全店内部账本差异”对比销售单累计已收与付款明细之和，不随营业日期变化，不重复汇总库存镜像流水，也不代表外部收银金额已经对账。
- 报表金额是整数欧分；罗马本地午夜区间含开始、不含次日开始，覆盖夏令时 23 / 25 小时营业日。
- 每页待办 30 条；每单最多返回 100 个异常（未结优先）和 50 条最近事件，并显示截断提示。完整事件在数据库保留。

## 开发与支持

复用原单台销售、付款、交付和打印 API。新增 POST BFF 接口：

| 路径（`/api/repairdesk/` 下）      | 输入 / 责任                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| `inventory/sales/workflow/read`    | `sale_order_id`，读取凭证、跟进、异常、操作历史、可选负责人及能力                          |
| `inventory/sales/workflow/command` | `sale_order_id`、`expected_workflow_version`、`idempotency_key`、`command`、严格 `payload` |
| `inventory/sales/workflow/report`  | `business_date`、`offset`、`limit`，当前待办与获授权财务汇总                               |

命令为 `fiscal.record`、`fiscal.verify`、`followup.set`、`issue.open`、`issue.resolve`。门店和操作者来自认证会话，不能由客户端指定。客户端入口仍是 `@/lib/repairdesk/api`。状态、事件、库存 revision 同事务提交；服务端广播仅发送失效元信息。原交易、付款、库存和保修事实保持原有写入链。

旧销售单在第一次操作前为 workflow version 0，无历史数据回填。每次编辑固定打开时版本；冲突后刷新核对，不能静默覆盖。相同请求重试复用 UUID；已成功的收款不因列表刷新失败退回“重新收款”。

## 验证与恢复

- 数据与并发：[数据库验证和恢复说明](../supabase/tests/sales-workflow/README.md)。
- UI：`tests/e2e/product-sales-wired.spec.ts` 使用合成 API 数据驱动真实 React 页面，覆盖 390–1440 宽度、中英意、iPad 旋转及完整售卖 / 跟进 / 日报流程；不构造真实生产交易。
- 迁移先于应用发布；迁移失败或新 RPC 不可用时返回失败，不回退 mock 成功。
- 应用回滚到已核验的前一部署，保留新表、事件及所有业务资料。紧急关闭新工作流可撤销三个新 RPC 的 service_role EXECUTE；不能删除业务表作为回滚。

本文件是门店与支持的新操作来源；原交易、保修和打印约束继续见 [原销售发布说明](PRODUCT_SALES_RELEASE.md)。
