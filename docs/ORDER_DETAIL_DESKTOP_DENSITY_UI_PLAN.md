# 工单详情电脑端高密度布局计划书

Status: superseded

> 历史说明：本文旧三栏正文仅作历史记录；当前权威规范见 [`UI_PAGE_GENERATION_DECLARATION.md`](./UI_PAGE_GENERATION_DECLARATION.md)、[`COMPONENT_GENERATION_DECLARATION.md`](./COMPONENT_GENERATION_DECLARATION.md) 与 [`RESPONSIVE_DENSITY_PLAN.md`](./RESPONSIVE_DENSITY_PLAN.md)，统一采用员工优先两列工单详情工作面（报价处理 → 客户与设备 → 关键信息与记录，`768px+` 约 `2fr/1fr`）。

Owner: UX / Frontend / Integration Lead
Scope: `/orders` 列表内打开的工单详情 Dialog，以及桌面宽度下的 `/orders/[id]` 详情工作面
Out of scope: 数据库、订单状态机、付款规则、通知发送规则、移动端信息层级重设计
Last planned: 2026-07-07 CEST

## 1. 目标

当前工单详情在电脑端不是缺少信息，而是把移动端/弹窗内容按屏幕宽度直接拉伸，导致部分卡片过宽、照片区被横向撑大、视觉焦点分散。新的桌面规划要把它改成维修店使用的高密度工作台：

- 一屏优先看清：工单状态、下一步、客户、设备故障、报价尾款、照片/签名/记录入口。
- 大屏不无限拉宽内容，宽屏只增加可读空间或辅助信息，不把单个卡片拉成横条。
- 1024、1280、1440、1536 宽度都有独立布局策略，不用同一套比例硬撑。
- 移动端继续沿用 RepairOS Floating Card，不把桌面方案倒灌到手机端。

## 2. 当前问题判断

### 2.1 弹窗外壳过度扩张

当前工单详情 Dialog 需要与“新建工单”保持同一类工作台外壳：接近全屏、固定 viewport-safe 高度，并保留列表上下文。对订单详情这种高频处理面来说，宽度应由共享 workspace shell 控制，避免每个入口散落单独宽高覆盖。

目标：桌面工单详情 Dialog 外壳与 `componentOverlay.formWorkspace` 使用同一宽度逻辑，最大为 `min(1400px, calc(100vw - 32px))`。内部三列仍由 `detailWorkspace.orderDetailGrid` 控制密度，不能因为外壳变宽而让单个业务卡片无限拉伸。

### 2.2 主内容只有第一排三列，第二排缺少规划

当前概览主区有客户 / 设备与故障 / 报价处理三列，但设备照片、关键信息、通知历史、时间线等下方区域更像“继续往下堆”。在电脑端这会造成：

- 设备照片横跨太宽，空占位看起来像被拉长。
- 次要信息没有明确边界，滚动后视觉节奏变松。
- 底部操作条和正文内容竞争空间。

目标：桌面概览应是“主三列 + 次级两/三栏”的工作台，而不是一列纵向堆叠。

### 2.3 设备照片应是证据缩略区，不是大横幅

设备照片在详情中是快速确认入口，不应该在概览页占满整行宽度。概览只显示固定尺寸缩略图、数量和拍照入口；大图查看走照片预览弹窗。

目标：照片面板宽度不超过主设备列宽，缩略图高度固定，不随弹窗宽度拉伸。

### 2.4 桌面端需要“信息压缩”，不是“信息隐藏”

客户电话、IMEI、故障描述、诊断结果、报价项目、审批/收款状态都要保留，但用字段矩阵、短行、二行摘要、截断和展开入口控制密度。

## 3. 桌面布局总方案

### 3.1 推荐工作面尺寸

| Viewport | Dialog 外壳 | 内容策略 |
| --- | --- | --- |
| 1024-1199 | `min(1400px, calc(100vw - 32px))` | 两栏：左侧信息流，右侧报价/动作 |
| 1200-1439 | `min(1400px, calc(100vw - 32px))` | 三列主工作台 |
| 1440-1535 | `min(1400px, calc(100vw - 32px))` | 三列固定密度，外壳接近新建工单 |
| >=1536 | `1400px` 上限 | 背景露出更多，内部卡片不无限拉伸 |

高度固定为 `calc(100svh - 32px)` 左右。Hero 和底部 action dock 固定在工作面内，正文独立滚动。

### 3.2 桌面整体结构

```txt
┌──────────────────────────────────────────────────────────────┐
│ Hero：工单号 / 状态 / 辅助标签 / 主流程 / 打印更多编辑关闭     │
├──────────────────────────────────────────────────────────────┤
│ Context strip：创建 / 负责人 / 门店或外修 / 最近记录          │
├───────────────┬────────────────────────────┬─────────────────┤
│ 客户信息       │ 设备与故障                  │ 报价处理         │
│ 250-280px     │ 420-480px                  │ 280-320px       │
├───────────────┼────────────────────────────┼─────────────────┤
│ 关键信息/通知  │ 设备照片                    │ 最近时间线摘要    │
│ 250-280px     │ 420-480px                  │ 280-320px       │
├──────────────────────────────────────────────────────────────┤
│ Bottom dock：金额摘要 + WhatsApp / 流转 / 收款                 │
└──────────────────────────────────────────────────────────────┘
```

核心原则：三列都有明确最大宽度；第二排跟随同一列宽，不出现单个 full-width 照片区。

## 4. 分区规划

### 4.1 Hero 顶部区

目标高度：`96px - 118px`，不因宽屏变高。

内容保留：

- 左侧：工单号、主状态、外修/送修/审批等辅助 badge、创建时间、负责人、门店。
- 右侧：打印、更多、编辑/保存/取消、关闭。
- 中部下方：当前流程、下一步、五段主流程进度。

优化规则：

- 进度条在桌面只显示 5 个主节点：接单、检测报价、维修处理、通知取机、收款完成。
- 外修、送修、审批、待收款不混进主流程，只作为 badge。
- 操作按钮优先图标 + tooltip；编辑状态才显示“保存 / 取消”文字。
- Hero 不承载大段说明，长提示放到流程面板或记录区。

### 4.2 Context strip

目标高度：`42px - 52px`。

布局：

- 1200px 以上：4 个紧凑 tile 一行。
- 1024-1199：2 x 2 小网格。
- 最近记录 tile 固定为最长，但宽度不超过 `320px`。

字段：

- 创建时间。
- 负责人。
- 门店 / 外修供应商。
- 最近一条记录：标题一行 + 时间/操作人一行 + “记录”入口。

不再把这些信息在其他卡片里重复大号展示，避免占高。

### 4.3 客户信息列

推荐宽度：`250px - 280px`。

内容顺序：

1. 客户姓名。
2. 主电话。
3. 备用电话，最多展示 2 个 pill，多余显示 `+N`。
4. 客户签名。

密度规则：

- 电话保持可点击联系菜单，但 pill 高度不超过 `26px`。
- 客户签名概览高度固定为 `40px - 48px`；签名采集/重签按钮保持在标题右侧。
- 不在客户列展示技师，技师已在 Context strip。
- 客户说明文字只在编辑态显示，阅读态隐藏或放 tooltip。

### 4.4 设备与故障列

推荐宽度：`420px - 480px`，是三列中最大的一列。

结构：

- 第一行：品牌 / 型号，两列。
- 第二行：IMEI / 序列号 + 扫码/复制/清空等图标动作。
- 第三行：设备备注 / 留存备注，两列。
- 第四行：手机密码，默认遮挡，查看后自动遮挡。
- 第五行：故障描述 / 诊断结果，两列摘要。
- 第六行：质保。

密度规则：

- 故障描述和诊断结果在桌面概览中最多 2 行，超出提供“展开”或 title。
- IMEI 使用等宽字体，一行截断，完整值通过复制或 tooltip 查看。
- 手机密码是敏感信息，不因为重排而扩大显示面积。
- 扫码、查看密码、复制等使用 icon button，不使用长文字按钮。

### 4.5 报价处理列

推荐宽度：`280px - 320px`。

内容顺序：

1. 总额 / 定金 / 尾款三格 money strip。
2. 审批状态 + 收款状态。
3. 报价项目列表。
4. 编辑态金额输入和保存提示。

密度规则：

- money strip 每格高度 `36px - 44px`，金额等宽数字。
- 报价项目每行高度 `46px - 58px`，名称、备注、金额同一行组内完成。
- 项目超过 3 条时，概览列内滚动或折叠显示 `+N 项`，避免撑高整个三列。
- 报价列可在正文滚动中 sticky 到上方，方便边看设备边收款。

### 4.6 设备照片区

推荐位置：第二排中列，跟随设备列宽。

推荐尺寸：

- 面板宽度：`420px - 480px`。
- 缩略图：3 或 4 格，单格高度 `56px - 72px`。
- 空状态：正面、背面、补拍三个固定小格，不出现 full-width 大空框。
- 保存照片数量放在标题右侧或底部一行，不单独占宽。

交互：

- 点击缩略图打开照片预览 Dialog。
- “拍照 / 补拍”是标题右侧按钮或最后一个 tile。
- 概览只看缩略图；不在概览展开大图。

验收硬线：

- 1440 宽度下 `data-order-panel="photos"` 宽度不超过 `500px`。
- 空照片状态的单个占位块高度不超过 `72px`。

### 4.7 关键信息、通知与时间线

这些内容是追溯辅助，不应和主三列抢首屏。

推荐布局：

- 第二排左列：关键信息 + 通知摘要。
- 第二排右列：最近时间线摘要。
- 完整记录仍保留“记录”入口或独立记录区域。

展示规则：

- 关键信息用 4 行以内：创建、完成、交付、外修供应商。
- 通知历史默认显示数量和最近一条，没有记录时显示一行空状态。
- 时间线概览显示最近 2 条，完整列表通过“记录”跳转到下方记录区。

### 4.8 底部操作条

目标：不遮挡正文，不变成大面积第二个面板。

结构：

- 左侧：总额 / 定金 / 尾款 / 状态摘要。
- 右侧：WhatsApp、流转、收款。

规则：

- 在 1200px 以上保持一行。
- 在 1024-1199 可变成两行：金额摘要一行，操作一行。
- 按钮高度 `36px`，图标 `14px - 16px`，文字 `12px`。
- 编辑报价时继续禁用 WhatsApp / 流转 / 收款，避免草稿未保存。

## 5. 断点细则

### 5.1 1024-1199：紧凑桌面

```txt
Hero
Context 2x2
┌──────────────────────────┬──────────────┐
│ 设备与故障                │ 报价处理      │
│ 客户信息                  │ 最近记录      │
│ 设备照片                  │ 关键信息      │
└──────────────────────────┴──────────────┘
Bottom dock 2 行
```

说明：这个宽度不强求三列同屏，优先保证设备和报价清楚。客户信息下沉到左侧信息流，避免三列太挤。

### 5.2 1200-1439：标准桌面

```txt
客户 260 | 设备 450 | 报价 300
关键信息 | 照片 450 | 时间线
```

说明：这是主要设计基准，也是当前 1280/1440 截图应重点优化的状态。

### 5.3 >=1440：宽桌面

不要继续拉伸卡片。策略是：

- 工作台最大宽度 `1160px - 1200px`。
- 居中显示，背景列表可见。
- 如果未来要利用超宽空间，应增加右侧“处理队列/相邻工单”这类新业务面板，而不是把现有详情卡拉宽。

### 5.4 <768：移动端

继续使用当前 RepairOS Mobile Detail Standard：

- `repairOs.mobileFloatingPage`。
- `repairOs.mobileFloatingHeader*`。
- `repairOs.mobileInfoCard`。
- 顶部悬浮卡、正文信息卡、底部操作条。

本计划不重排移动端。

## 6. 状态与异常

### 6.1 Loading

Skeleton 必须模拟最终布局：

- Hero skeleton 固定高度。
- Context strip skeleton。
- 主三列 skeleton。
- 第二排 photos / records skeleton。

不要再用几个 full-width skeleton 条代替，否则加载状态和真实状态跳动太大。

### 6.2 Empty

- 无照片：固定三格小占位。
- 无通知：一行 muted 文案。
- 无时间线：一行 muted 文案，但工单创建记录通常应存在。
- 无备用电话：不显示备用电话块，释放客户列空间。

### 6.3 Error

详情加载失败保留在工作面内，不撑成整页大错误卡：

- 标题：工单详情加载失败。
- 原因：一行或两行。
- 操作：重新加载。

### 6.4 Long content

- 客户名、电话、IMEI、供应商、设备备注：一行截断。
- 故障描述、诊断结果：最多两行。
- 报价项目名：一行，备注一行。
- 时间线摘要：一行标题 + 一行元信息。

完整内容通过展开、tooltip、复制、记录区或预览弹窗访问。

## 7. 可访问性与操作

- 所有 icon button 必须有 `aria-label` 或 tooltip。
- Dialog 保留 `DialogTitle` 和 `DialogDescription`，视觉隐藏可以继续用 `sr-only`。
- 照片缩略图按钮 `aria-label="查看照片 <文件名>"`。
- 金额、电话、IMEI 不仅靠颜色表达状态。
- 键盘 Tab 顺序：Hero 操作 -> Context 记录入口 -> 客户联系 -> 设备动作 -> 报价编辑 -> 照片 -> 底部动作。
- 关闭按钮保持右上角可见，不能被 Hero 操作挤压。

## 8. 实施建议

### WP-01 固定桌面工作面宽度

- 调整 `componentOverlay.detailWorkspace` 或新增 `componentOverlay.orderDetailWorkspace`。
- 移除工单详情在 `xl/2xl` 下放大到 `1320px/1560px` 的行为。
- 保留新建工单等表单工作面的宽尺寸，不要全局收窄所有 Dialog。

退出标准：

- 1440/1536 下工单详情 Dialog 不超过约 `1200px`。
- 其他宽屏 Dialog 不受误伤。

### WP-02 重建桌面概览 Grid

- 将当前主 grid 改为统一使用 `detailWorkspace.orderDetailGrid` 或新的 `orderDetailDesktopGrid`。
- 加入第二排 grid：关键信息/通知、设备照片、时间线摘要。
- 1024-1199 使用两栏布局，不硬塞三列。

退出标准：

- 1280/1440 下主三列和第二排对齐。
- 1024 下没有横向滚动，内容可读。

### WP-03 压缩设备照片面板

- `DesktopOrderPhotosPanel` 不再 full-width。
- 缩略图固定高度，空状态固定三小格。
- 标题右侧保留拍照按钮，数量作为轻量 meta。

退出标准：

- 照片面板在 1440 下不超过 `500px` 宽。
- 无照片状态不出现拉长大框。

### WP-04 调整底部 Action Dock

- 1200px 以上保持一行。
- 1024-1199 自动两行。
- 金额摘要使用更紧凑的 `OrderWorkspaceMoneyStrip compact`。

退出标准：

- Dock 不遮挡正文最后一行。
- 三个主动作在 1024 下文字不溢出按钮。

### WP-05 补充视觉回归测试

- 更新或新增桌面 UI audit。
- 断言无页面级横向滚动。
- 断言 Dialog 和照片面板 bounding box。
- 产出 1024、1280、1440、1536 截图。

退出标准：

- `npm run lint`
- `npm run typecheck`
- `npm run test`
- `npm run build`
- 相关 Playwright 视觉/overflow 检查通过或记录环境阻塞原因。

## 9. 验收清单

### 视觉验收

- 1024：两栏紧凑桌面，不横向滚动。
- 1280：客户 / 设备 / 报价三列清楚，第二排对齐。
- 1440：工作台不再被拉得过宽，照片区保持固定缩略图密度。
- 1536：Dialog 不继续放大到 1500px 以上。
- 移动端 390：仍然是 RepairOS Floating Card，未被桌面方案影响。

### 信息验收

- 首屏可见工单号、当前状态、下一步、客户、主电话、设备、IMEI、故障、报价、尾款、照片入口。
- 记录入口可见，最近记录能快速判断刚发生了什么。
- 未付款、待审批、外修/送修状态仍然明确。
- 长字段不会撑开布局。

### 交互验收

- 点击电话仍可联系客户。
- 点击拍照/补拍仍进入原有上传流程。
- 点击照片缩略图打开预览。
- 点击流转在当前详情内展开，不再嵌套第二个大弹窗。
- 编辑报价时外部动作保持禁用。

### 技术验收

- `document.documentElement.scrollWidth <= window.innerWidth`。
- `data-order-detail-dialog-shell` 宽度在 1440 下不超过计划上限。
- `data-order-panel="photos"` 宽度在 1440 下不超过 `500px`。
- 所有 flex/grid 子项保留 `min-w-0`。
- 不新增硬编码颜色，继续使用 `src/styles.css` token。

## 10. 推荐实施顺序

1. 先改 Dialog 宽度上限，快速解决“大屏拉长”的根因。
2. 再重排概览 grid，把照片和记录纳入第二排规划。
3. 然后压缩照片面板和底部 action dock。
4. 最后补视觉截图和 overflow 测试。

这样可以每一步单独验证，避免一次性重写整个订单详情页。
