# 店铺状态与关闭：小白友好版完整规划

> Task: `TASK-20260719-004-store-lifecycle-uuid-flow-plan`
>
> Plan Delta: 2026-07-20，小白操作优先版
>
> 状态：规划完成，等待 Owner 批准实施
>
> 风险：T3 / R4 / L1

## 1. 最终建议

把当前像“运维控制台”的店铺生命周期区域，改成普通老板也能完成的引导式流程：

1. **检查是否可以关闭**；
2. **处理检查发现的问题**；
3. **确认并关闭这家店（可恢复）**。

页面任何时候只显示一个主要任务和一个主按钮。重命名移回“店铺资料”，不再与关闭并排；UUID、revision、capability、AAL2、migration、RPC 等技术词不进入主流程。

当前 ChinaTech 的店铺唯一编号是：

```text
5248dda1-2b32-46cd-8ed0-d15386a9e8ed
```

关闭确认使用最后 8 位：

```text
86a9e8ed
```

主页面称它为“店铺唯一编号”，并解释“店名可以修改，这个编号不会改变”。最后 8 位用于避免选错同名店铺，不是密码。

## 2. 小白体验成功标准

用户打开页面 5 秒内，应能回答：

- 我现在操作的是哪家店？
- 这家店现在是正常、正在关闭，还是已关闭？
- 关闭是不是永久删除？
- 能不能恢复？
- 下一步只需要做什么？
- 如果不能继续，应该去哪里处理？

不要求用户理解 UUID、预检、TOTP、状态版本、功能开关或数据库迁移。

## 3. 页面设计原则

### 3.1 一屏只做一件事

- 未检查时，只显示“检查是否可以关闭”。
- 检查被阻断时，只显示问题和处理入口。
- 检查通过时，只显示影响和“继续关闭”。
- 最终确认时，才显示尾号、原因和验证码。
- 已关闭时，只显示状态、影响和恢复入口。

### 3.2 先说结果，再解释技术

主文案使用：

- “可以继续关闭”；
- “暂时不能关闭”；
- “检查结果已过期，请重新检查”；
- “正在确认结果，请不要重复点击”；
- “店铺已进入关闭流程”。

技术原因只放进“了解详情”，供高级用户或客服排查。

### 3.3 危险操作渐进出现

- 设置首屏不出现红色最终关闭按钮。
- 未通过检查时不渲染关闭确认表单。
- 验证码不常驻在页面底部。
- 最终按钮不自动获得焦点，按 Enter 不能直接关闭。
- 永久删除不出现在浏览器页面。

## 4. 设置页入口重新布局

### 4.1 店铺资料

```text
店铺资料
├─ 店铺名称：ChinaTech                    [修改名称]
├─ 地址、电话、WhatsApp、邮箱
├─ 店铺唯一编号：5248...e8ed             [复制]
└─ 说明：店名可以修改，这个编号不会改变
```

规则：

- “修改名称”是独立、低频的普通设置动作。
- 重命名使用自己的确认弹层和 6 位安全验证码。
- 若收据/客户消息名称被单独定制，默认不覆盖，并展示修改前后值。
- 完整唯一编号可以复制，但不作为密码或权限依据。

### 4.2 店铺状态与关闭

```text
店铺状态与关闭
├─ 当前店铺：ChinaTech
├─ 当前状态：正常使用
├─ 说明：关闭前会检查未完成工单、未结金额和店内设备
├─ [检查是否可以关闭]
└─ 了解详情
```

首屏不显示：

- 关闭原因输入；
- 店铺名称确认输入；
- 店铺编号尾号输入；
- 6 位验证码；
- revision、challenge、operation ID；
- 归档、导出、永久清除技术块。

## 5. 三步关闭流程

### 第一步：确认店铺并检查

主按钮：

```text
检查是否可以关闭
```

辅助说明：

```text
这一步只检查，不会修改、关闭或删除任何资料。
```

系统自动确认当前店铺，并检查：

- 是否还有未完成工单；
- 是否还有未结金额；
- 是否还有客户设备或店内保管事项；
- 是否有正在执行的后台任务或离线写入；
- 是否存在会影响关闭的店铺状态。

邀请、客户 iPad 等会在关闭时自动停止的项目，应显示为“关闭时会自动处理”，不能混入必须由用户先处理的问题。

### 第二步：查看检查结果

#### A. 可以继续

```text
✓ 可以继续关闭

当前店铺：ChinaTech
店铺识别码最后 8 位：86a9e8ed        [复制]
检查结果将在 8 分钟后失效

关闭后会：
• 停止新建和修改订单、客户、库存等数据
• 停止旧邀请和客户 iPad 访问
• 保留现有资料，以后可以由店铺主账号恢复

[继续关闭]
了解检查详情
```

“继续关闭”只打开最终确认层，不执行关闭。

#### B. 暂时不能关闭

```text
暂时不能关闭

请先处理：
• 还有 3 张工单尚未完成              [查看工单]
• 还有 €20.00 尚未处理               [查看付款]
• 还有 1 台客户设备在店内            [查看工单]

[处理后重新检查]
了解检查详情
```

只显示真正存在的问题；计数为零的项目不占页面。

#### C. 检查失败

```text
暂时无法完成检查
没有对店铺做任何更改。

[重新检查]
```

技术错误和支持编号放在“了解详情”，不得向普通用户展示原始数据库错误。

### 第三步：确认并关闭

桌面使用小型 Dialog；移动端使用接近全屏 Sheet。

```text
确认关闭 ChinaTech？

这不是永久删除。关闭后资料继续保留，以后可以恢复。

现在关闭会：
• 立即停止日常新建和修改
• 停止旧邀请和客户 iPad 访问
• 切换到另一家可用店铺；没有其他店时进入“已关闭店铺”

店铺识别码最后 8 位
[请输入上方显示的 8 位字符]
说明：用于避免关错同名店铺，不是密码

关闭原因
[停止营业 ▾]

身份验证器中的 6 位安全验证码
[      ]
说明：例如 Google Authenticator，不是短信验证码

□ 我明白这是可恢复关闭，不是永久删除；旧邀请和客户 iPad 权限不会自动恢复

[返回检查]   [确认关闭这家店（可恢复）]
```

#### 为什么不再要求手输店铺名称

店铺名称和编号尾号都是对同一目标的重复确认。小白版只保留更稳定的编号尾号、明确后果勾选和 6 位安全验证码：

- 用户仍需主动输入或粘贴尾号，不自动填充；
- placeholder 不显示真实答案；
- 页面持续显示店铺名称；
- 服务端继续绑定完整 store UUID、revision、action 和有效检查结果；
- 服务端仍校验当前真实店铺名称/目标状态，但不要求用户重复手打。

## 6. 提交中、未知结果与成功

### 6.1 提交中

```text
正在安全关闭店铺…
请不要重复点击或关闭页面。
```

- 禁止双击和重复提交；
- 固定使用同一个 operation ID；
- 关闭按钮变成明确的处理中状态；
- 保留取消离开提示，但不取消已发出的服务端操作。

### 6.2 网络结果未知

```text
正在确认关闭结果
网络刚才中断，系统正在核对，请不要重新提交。
```

客户端先查询原操作结果，不能生成新的关闭请求。确认前一次已经完成时，显示：

```text
已确认前一次操作已经完成
```

### 6.3 关闭成功

```text
店铺已进入关闭流程

✓ 新建和修改已经停止
✓ 现有资料继续保留
✓ 旧邀请和客户 iPad 访问已经停止

至少一小时后完成归档。

[前往当前可用店铺]
[查看已关闭店铺]
```

成功不能只显示短暂 toast，必须有持久结果页或结果卡。

## 7. 已关闭店铺与恢复流程

普通店铺选择器只列正常使用的店铺。正在关闭或已关闭的店铺进入专用“已关闭店铺”页面：

```text
已关闭店铺
└─ ChinaTech
   ├─ 状态：已关闭，可以恢复
   ├─ 关闭时间：2026-07-20 00:15
   ├─ 识别码尾号：86a9e8ed
   └─ [查看与恢复]
```

恢复确认：

```text
恢复 ChinaTech？

恢复后：
• 可以重新进入店铺并继续营业
• 订单、客户和库存资料仍然保留
• 旧邀请、旧链接、客户 iPad 凭据和已停用员工不会自动恢复

身份验证器中的 6 位安全验证码
[      ]

[取消]   [确认恢复营业]
```

成功后显示“店铺已恢复使用”并提供“进入店铺”。

## 9. 默认展示与“了解详情”

### 始终展示

- 当前店铺名称；
- 当前状态；
- 当前唯一主动作；
- 真正阻止继续的问题；
- 检查结果剩余分钟；
- 尾号确认要求；
- 立即影响、资料保留、可以恢复；
- 旧访问不会自动恢复；
- 无权限或功能不可用的白话原因。

### 默认隐藏

- 完整 UUID（店铺资料区仍可复制）；
- revision、snapshot hash、challenge、operation ID；
- capability code、AAL2、CAS、writer fence、RPC；
- feature flag 名称和值；
- migration、数据库、cookie、worker 状态；
- 计数为零的检查项目；
- 原始 SQL/Supabase 错误；
- export manifest、hash 和后台任务细节；
- purge 内部状态。

同名店铺时，应把地址、创建日期或稳定店铺代码临时提升到主页面帮助辨认。

## 10. 权限行为

| 用户                                  | 页面行为                                             |
| ------------------------------------- | ---------------------------------------------------- |
| 店铺主账号                            | 可检查、关闭和恢复                                   |
| 其他 owner membership                 | 只显示准确的无权限原因，不显示编号、验证码和执行按钮 |
| manager / technician / sales / viewer | 不显示危险操作；可显示普通状态摘要                   |
| platform support                      | 不因平台身份获得店铺业务关闭能力；走独立审批路径     |
| 无明确当前店铺                        | 先要求选择并确认店铺，不显示关闭表单                 |
| 店铺正在关闭或已关闭                  | 只进入“已关闭店铺”恢复页面                           |

前端隐藏只改善体验；所有权限必须继续由服务端验证。

## 12. 移动端、桌面端与无障碍

### 移动端

- 一次只显示一个主按钮；
- 最终确认使用接近全屏 Sheet；
- Sheet 正文可滚动，底部动作在安全区内；
- 键盘打开后，验证码和最终按钮仍可操作；
- input/select 字号至少 16px，触控区域至少 44px；
- 尾号单行等宽，完整编号在详情内 `break-all`；
- 390×844、430×932 不得横向溢出。

### 桌面端

- 关闭区域保持单列，最大宽度约 680px；
- 不做多列运维仪表盘，不并排展示重命名与关闭表单；
- 最终确认使用 `modalSm` / `modalMd` 小型 Dialog；
- 危险按钮不自动获得焦点；
- 768、1024、1280、1440 下长意大利语文案不溢出。

### 无障碍

- 所有输入有可见 label 和说明关联；
- 状态变化使用 `role="status"` / `aria-live="polite"`；
- 复制成功明确播报，但不自动填值；
- 错误不只靠颜色；
- Dialog/Sheet 有 title、description 和正确焦点返回；
- 屏幕阅读器能听到店铺名、影响、错误和下一步。

## 13. 后台不能因为页面变简单而削弱

小白化只发生在展示层。生产关闭前，后台必须继续或补齐：

- 服务端店铺主账号校验；
- 精确完整 UUID 与明确当前店铺绑定；
- store、revision、action、有效检查结果绑定；
- 近期 MFA/TOTP 与一次性 challenge；
- 持久 writer fence；
- 关闭事务内重新计算阻断项；
- 普通业务 GET/POST 在 closing/archived 时 fail closed；
- 关闭后 Cookie、工作区、缓存和其他设备上下文切换；
- 邀请、客户 iPad、离线写入和后台任务失权；
- 固定 operation ID、幂等冲突与未知结果核对；
- 成功、拒绝、重试和恢复审计；
- 恢复不复活旧邀请、Kiosk token、配对码或已停用成员；
- 浏览器继续没有永久删除入口。

当前实现仍有写入隔离、事务内复检、关闭后上下文等安全阻断，生产关闭功能必须保持不可用，直到这些门禁完成并验证。

## 14. 实施优先级

### Must：生产关闭前必须完成

#### WP-00 — 基线与合同

- 从最新 `origin/main` 建隔离工作树；
- 只读确认生产 schema、flags、linked migration history；
- 冻结小白文案、三步流程、权限和错误码。

#### WP-01 — 设置页简化

- 重命名移至店铺资料；
- 生命周期改名“店铺状态与关闭”；
- 首屏只保留状态、说明和检查按钮；
- 完整唯一编号放店铺资料并提供复制。

#### WP-02 — 三步关闭向导

- 通过、阻断、失败、过期完整状态；
- 倒计时和直接处理入口；
- 专属最终确认层；
- 删除手输店铺名，保留尾号、原因、后果确认和验证码。

#### WP-03 — 服务端 capability 与白话错误

- 返回店铺主账号、明确店铺、MFA、功能开放、写入保护状态；
- 页面填写前显示可用性；
- 原始错误映射为稳定 code 和白话文案。

#### WP-04 — 原子关闭与上下文

- 建立数据库写入栅栏；
- 事务内重算关闭阻断；
- 修复普通 GET/POST、邀请、客户 iPad、离线和后台任务写入边界；
- 关闭后自动切换其他正常店铺或进入无店铺/已关闭店铺页面。

#### WP-05 — 恢复页面

- 普通业务店铺与已关闭店铺分离；
- 恢复确认和验证码；
- 明确旧凭据不复活；
- 恢复成功后进入店铺。

## 15. Given / When / Then 验收

1. Given 店铺正常且未检查，When 打开页面，Then 只显示当前店铺、状态、说明和“检查是否可以关闭”。
2. Given 页面支持重命名，When 查看关闭区域，Then 不出现重命名表单；修改名称入口位于店铺资料。
3. Given 点击检查，When 请求进行中，Then 唯一主按钮显示“正在检查店铺…”，不能重复发起。
4. Given 检查通过，When 显示结果，Then 看到“可以继续关闭”、尾号、剩余时间和三条主要影响，但看不到验证码。
5. Given 检查发现问题，When 显示结果，Then 只显示真实问题和处理入口，完全不显示关闭表单。
6. Given 检查失败，When 显示错误，Then 明确“没有做任何更改”并提供重新检查。
7. Given 倒计时归零，When 页面未刷新，Then 自动回到重新检查状态并清空确认、验证码和 challenge。
8. Given 点击“继续关闭”，When 最终确认层打开，Then 显示准确店铺、尾号、立即影响、资料保留和恢复说明。
9. Given 未输入正确尾号、原因、后果勾选或验证码，When 尝试提交，Then 最终按钮不可用并逐项提示。
10. Given 复制尾号，When 复制成功，Then 宣告“已复制”，但不自动填入确认字段。
11. Given 用户不是店铺主账号，When 打开页面，Then 不显示识别码、验证码或执行按钮，只显示准确原因。
12. Given 没有 MFA 或保护门禁未就绪，When 打开页面，Then 在填写前显示下一步或“功能暂时不可用”。
13. Given 确认期间切换店铺、revision 变化或检查过期，When 状态变化，Then 当前确认立即失效。
14. Given 双击、连续按 Enter 或重复请求，When 尝试提交，Then 只产生一个 operation。
15. Given 网络超时，When 连接恢复，Then 先核对原 operation，不创建新的关闭意图。
16. Given 关闭成功，When 页面刷新，Then 原店铺不能继续作为普通业务店铺访问。
17. Given 有第二家正常店铺，When 关闭成功，Then 自动切换到该店；没有时进入“已关闭店铺”。
18. Given 恢复成功，When 进入店铺，Then 旧邀请、旧客户 iPad 凭据和已停用成员没有被描述或实际恢复。
19. Given 中文、意大利语、英语长文案，When 在 390、430、768、1024、1280、1440 验证，Then 无横向溢出、按钮竖排或遮挡。
20. Given 键盘/屏幕阅读器用户，When 完成流程，Then 状态、错误、焦点和主动作都可理解和操作。

## 16. 测试、发布与回滚

### 必跑验证

```text
npm run lint
npm run typecheck
npm run test
npm run build
```

另外必须覆盖：

- loading、eligible、blocked、expired、error 五种检查状态；
- primary owner、其他 owner、manager、staff、跨店 UUID；
- 无 MFA、错误/过期/重复验证码与 challenge；
- close 与订单、邀请、客户 iPad、离线和后台写入并发；
- 双击、Enter、返回、网络超时、replayed、revision conflict；
- 有/无其他正常店铺的关闭后落点；
- 恢复后旧权限不复活；
- 390×844、430×932、768×1024、1280×800、1440×900；
- 中文、意大利语、英语与屏幕阅读器。

### 发布顺序

1. 解决广泛生产数据库 NO-GO 和 linked migration-history gate；
2. migration 先应用，所有 lifecycle flags 保持关闭；
3. 先发布小白设置页、白话 capability 和只读检查；
4. 先启用并验证写入保护；
5. 仅 disposable test store 验证重命名、关闭和恢复；
6. Security/QA 复核和观察通过后，再单独批准生产关闭；
7. export/purge 保持关闭，等待独立 R4 项目。

### 立即暂停

- 关闭成功后仍能普通读写；
- 关闭事务不能重新计算阻断项；
- 没有第二家店时无法进入恢复页面；
- 未知结果会生成新 operation；
- linked migration、备份/恢复、RLS/grants 或 flags 状态不明确；
- 页面简化导致服务端授权或 MFA 被前端替代。

### 回滚

- UI/capability：回滚应用代码；服务端 optional 字段保持向后兼容；
- additive schema：保持 dormant，不在事故中 drop；
- 重命名：使用最新状态做前向重命名；
- 关闭/归档：走正式恢复并重新签发凭据；
- 不能关闭写入保护来回滚，因为会重新开放已关闭店铺写入。
