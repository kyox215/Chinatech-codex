# 角色权限配置计划书

Last updated: 2026-07-12
Owner: 鹤祥 / Chinatech
Status: Phase D2/E code completed globally; two production migrations pending independent database approval

## 目标

设置页中的角色配置必须变成可执行的权限系统，而不是只保存“技师/前台”等标签。每个成员进入系统后，服务端必须根据店铺角色判断：

- 可以查看哪些页面、列表、详情和附件。
- 可以编辑哪些业务字段。
- 是否能看到金额、利润、供应商、设备解锁、历史记录等敏感内容。
- 是否能执行批量操作、成员管理、设置修改、导出、退款、强制付款状态等高风险动作。

## 角色定义

| 角色              | 业务含义       | 默认权限定位                                                                   |
| ----------------- | -------------- | ------------------------------------------------------------------------------ |
| 店主 `owner`      | 店铺最高负责人 | 全部业务权限； owner 转移/移除仍需要额外审批                                   |
| 店长 `manager`    | 日常运营负责人 | 大部分订单、客户和设置权限；单张订单金额可见，汇总/利润/历史浏览需店主显式授权 |
| 技师 `technician` | 维修执行人员   | 仅本人稳定负责人范围；可看单张订单金额，不能看汇总/利润、导出或成员管理        |
| 前台 `sales`      | 接待/收款人员  | 接待、客户、收款、通知为主；不能调价/退款/看供应商成本/改流程                  |
| 只读 `viewer`     | 临时或审计查看 | 默认只读且需要对象范围；不能写入、导出或查看敏感凭据                           |

## 敏感内容展示策略

### 金额

- 前台可以收款和查看客户应付金额，但不能修改维修报价、押金、退款或强制付款状态。
- 技师可查看分配给自己的单张订单总额、定金和尾款，但不能读取列表金额、全店汇总、利润、退款或金额调整入口。
- 店长/店主可以看金额详情和进行金额修正，必须写审计日志。

### 历史记录

- 店主默认可以浏览完整工单历史；店长需店主授予 `order:archive_browse` 后才能浏览归档。
- 前台可以查看客户接待必要历史，例如设备、问题、近期工单状态；不默认展示利润、供应商成本、内部敏感备注。
- 技师只看分配给自己或当前维修范围内的历史，重点是设备问题、诊断、照片和维修记录。
- 只读角色必须是范围内只读；不得成为“全店所有敏感历史”入口。

### 供应商和成本

- 供应商、采购成本、订单供应商选择默认只给店主。
- 店主可单独授予 `supplier:read`、`supplier:assign`、`supplier:manage`。
- 授权表必须启用 RLS，普通客户端不能直接读写，通过服务端校验后写入。

### 设备解锁和附件

- PIN、密码、图案、签名链接、照片签名 URL 等属于高敏感信息。
- 技师只有在范围满足时读取，并记录审计。
- 前台读取解锁信息需要更高审批或后续独立流程；不得默认开放。

## 服务端执行原则

- UI 可以隐藏按钮，但真正的权限必须在 API/Repository 层执行。
- 所有高风险动作必须使用统一权限矩阵，不允许在单个页面里临时判断角色字符串。
- 拒绝策略采用 fail-closed：没有明确允许即禁止。
- 系统 actor 默认不绕过权限，除非测试/维护上下文显式声明。
- 高风险动作写审计日志，至少包括 actor、store_id、action、entity_type、entity_id、时间和输入摘要。

## 数据库策略

- 继续使用单一共享数据库和 `store_id` 隔离。
- 新增或已有授权表必须：
  - 启用 RLS。
  - 撤销 `anon` / `authenticated` 直接表权限。
  - 只允许 service role 通过服务端业务逻辑写入。
  - 使用唯一索引避免同一成员重复有效授权。
- 本阶段使用 `store_member_permission_grants` 管理供应商权限授权。
- 生产数据库应用不能只凭本地 migration 文件存在来认定完成；必须先通过 `docs/SHARED_DB_TENANT_ONBOARDING_EXECUTION_PLAN.md` 的 Database Application Gate。
- 2026-07-12 read-only CLI recheck: `supabase db push --linked --dry-run --include-all` 只列出本任务两份待应用 migration，未执行生产写入。

- 仅有历史搜索权限的角色只能用完整工单号、电话或 IMEI 精确命中，最多返回 20 条且不可翻页枚举；浏览全部历史需要 `order:archive_browse`。

### Phase E: 设置页可视化配置

当前状态：

- 在设置页成员管理中展示角色说明和敏感权限摘要。
- 店主可以授予供应商权限，并可仅向店长授予历史浏览、店铺金额汇总、成本/利润三项敏感权限。
- 技师、前台和只读角色不能通过成员 grant 获得汇总、利润或历史浏览硬禁止能力。
- 角色改变、停用和恢复通过单事务 RPC 更新成员并撤销旧 grants；权限集合本身也通过持有 membership 行锁的单事务 RPC 做“最后一次完整集合覆盖”，避免并发请求形成权限并集。
- 店铺权限上下文每 15 秒、窗口聚焦和网络恢复时主动刷新；权限指纹变化会在绘制前重置敏感查询并重挂页面子树。退出登录同时清理 RepairDesk IndexedDB。

## 2026-07-12 全平台归档与员工权限实施

### 全局规则

- 规则作用于所有现有和未来店铺，不包含 ChinaTech 特例。
- `owner` 全店可见；`manager` 与前台可查看单张订单金额，但集合金额默认删除；`technician` 只能访问分配给自己 membership 的订单；`viewer` 默认拒绝订单和库存敏感读取。
- 批量流转仅店主/店长；批量打印和导出仅店主现有导出权限。店长与前台可打印其有权访问的单张工单，技术员仅可打印分配给自己的单张工单；只读成员不可打印。无批量能力时列表不显示批量打印入口。
- 完成和取消订单不修改数据库状态，只由统一函数派生为历史归档；付款、交付或设备返还矛盾继续保留在授权历史与单笔详情中。

### 待应用迁移

1. `20260712002317_global_staff_permission_grants.sql`：扩充 owner 管理的 grant 目录；增加成员角色/状态变化时原子撤销，以及成员完整权限集合原子替换的 service-role RPC。
2. `20260712003452_global_order_assignment_scope.sql`：增加 nullable 同店 `assignee_membership_id`、复合外键和查询索引；历史订单先按同店唯一活动成员显示名匹配，剩余订单保守分配给同店唯一活动店主，避免按同名猜测技术员。

2026-07-12 linked `supabase db push --linked --dry-run --include-all` 已通过，只列出上述两份 migration，未执行生产 apply。代码在迁移前保持非技术员旧流程兼容，负责人控件自动关闭，技术员订单访问默认拒绝；迁移后立即切换为 membership ID。生产应用、验证查询、观察窗口和回滚仍需单独批准。

### 残余生产门

- 既有 17 张旧 `public` 表的浏览器角色授权/RLS 风险不由本次 migration 自动处理；它仍是独立 Critical containment 工作包。
- 迁移后必须核对是否存在无唯一活动店主、无负责人或姓名匹配歧义的异常行；这些行只允许店主/店长处理，不能放宽技术员对象范围。

## 2026-07-10 客户读取接线状态

- `customers/list`、`customers/list-page`、`customers/search` 使用 `customer:list`。
- `customer/get`、`customers/devices`、`customers/intake-search` 使用 `customer:detail`；intake 返回设备/历史信息，不能按普通最小列表处理。
