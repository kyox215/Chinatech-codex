# Isolated Android v5 gate runtime tests

This APK is separate from the shipped application. It is signed with the existing project candidate identity only to instrument `in.chinatech.phoneassistant`. The production APK has no test receiver, debug activity, gate override, test signing key or test SAF provider.

Build target with `scripts/android-assistant/build-v5.sh`, then build this APK with `scripts/android-assistant/build-gate-runtime-tests.py`. Both outputs stay under ignored `.local/android-phone-gate/`. Install only on the two dedicated project emulators selected by the release owner; this script does not discover or operate devices.

Instrumentation component: `in.chinatech.phoneassistantgatetest/in.chinatech.phoneassistant.GateRuntimeTests`.

- `mode=setup, role=receive|send` creates or reads a guarded synthetic task and returns public device/job/TLS facts, fixed signing public key and metadata hashes. It never returns pairing secrets or private keys. `fresh=true` is accepted only after the previous synthetic task has a local terminal state; existing non-fixture tasks are preserved.
- `mode=storage-tls` after setup tests real Android Keystore device signing, encrypted AtomicFile reopen, mutual Keystore TLS positive/negative cases, actual Android SQLite additive 1→3 and 2→3 preservation, and old QR refusal. No website permission is fabricated.
- Host freezes a canonical `CTPA5P` plan from the setup facts. `mode=proof, plan64=<base64url UTF8 plan>` returns the real nonexportable device-key proof envelope for the actual `/api/toolbox/client/v1/phone-assistant/jobs/start` path. `localPeer=true` uses the same-device independent synthetic peer key/instance/job; it does not claim to be a second physical phone. Original start request/nonce are retained for idempotency. Generate timestamped proofs immediately before posting to the protected candidate.
- The release owner posts these public envelopes to the real protected candidate API, with the already-reviewed release registry and HTTPS canonical origin. Server signing private keys never leave Vercel. Give only the resulting public `kid.payload.signature` envelopes to `mode=verify, plan64=..., ownPermit=..., peerPermit=...`. This checks all role bindings, original journal/TLS reopen, changed-scope and swapped-role rejection. By default it ends the synthetic task as local `cancelled`, pending a real API outcome. `keepOpen=true` retains it for further recovery tests.
- To exercise the real receiver engine, create a fresh receive fixture. Build the common plan using its receiver facts plus `localPeer*` facts and `engineManifestHash`, count `2`, bytes `65537`. Obtain both real API permits via ordinary and `localPeer=true` proofs. Invoke `mode=engine, plan64=..., ownPermit=..., peerPermit=...`. It uses only the test APK's granted synthetic SAF provider. It verifies wrong-manifest refusal before any file write; zero/nonzero byte streaming and saved hashes; discarded `FINISHED` followed by same-plan, same-TLS receipt-only replay; no duplicate objects; completed close preserving its terminal state; and original destination restoration after deliberately changing the current directory. It does not assert physical hotspot or complete sender-engine acceptance.
- `mode=proof, operation=outcome` emits the original task's real device proof for its durable checkpoint/terminal result. A local peer outcome also needs the explicit matching `checkpointHash` and `terminal`. The release owner submits it to the protected candidate to close the actual synthetic jobs. No detection facts, filenames or content are uploaded.

Failures return a phase, safe exception type/code, numeric source line and assertion count. They never print exception messages with arbitrary content, pairing secrets or file data. Do not relax production verification or use a legacy CTSS4 peer to make these tests pass. JVM/SQLite/build/Android emulator/physical device/production evidence remain distinct.

## Real two-engine, normal three-code flow

A second instrumentation component, `in.chinatech.phoneassistantgatetest/in.chinatech.phoneassistant.GateTwoEndTests`, runs the actual sending and receiving engines on separate, explicitly selected project emulators. Set `role=receive` or `role=send`. With `cleanupFixture=true`, only an existing task explicitly marked `isolatedFixture` may be locally cancelled first; receipts and residuals are never cleared. Other pending original tasks cause refusal.

After installing the latest separate test APK on both devices, the release owner runs `python3 scripts/android-assistant/run-gate-two-end.py --receiver emulator-5580 --sender emulator-5582 --adb <project-adb>`. The two serials must be present in the project's saved emulator inventory. The helper uses temporary ADB forwards to device loopback ports 10082/10083, exchanging setup/response/final QR strings only in RAM. QR strings, Wi-Fi credentials and pairing secrets are never passed as shell arguments or written to logs. `CODE`, `APPLY`, `STATE`, `VERIFY` and `FINISH` are test-only IPC commands; production has no such server.

This path calls the normal website status/admission/outcome methods, normal source selection/freezing, `sendWithRecovery`, receiver metadata/object verification, `FINISHED`, durable outcomes and safe completion close. It requires the real canonical website to admit this exact release. It refuses a missing/paused/outdated registry; it neither seeds permits nor overrides the production gate. It verifies one empty and one 65537-byte source, actual saved destination hashes and receipts, sender's final peer ACK, both original durable completed records and real website outcome reporting. Existing emulator Wi-Fi is the stated network scope; automatic hotspot, physical brands and camera capture remain separate acceptance boundaries.

The helper writes only safe states and instrumentation summaries to `.local/android-phone-gate/runtime/two-end-result.json` and the two role logs. A coordination failure preserves the unknown original task rather than killing the engine or clearing the journal. Inspect the safe status/phase first; do not re-run a mutation blindly.

## Precisely identified interrupted synthetic job

`GateTwoEndTests` also supports the explicit `mode=cleanup-known`. It requires all three arguments `expectedInstallation`, `expectedJob` and `expectedScope` (exact UUID/UUID/SHA256), verifies the current task is the sending role and is not completed, and requires both frozen and selected source sets to contain exactly two unique URIs under this test APK's provider with the known empty/65537-byte hashes and the original full manifest digest. It rechecks the same task on the main thread before calling the unchanged production `engine.stop()` and `gate.flush()` methods. Cancellation must be durable and reported to the real website; receipts, residuals and journal entry counts must remain unchanged. A completed or unknown task is never cancelled by this mode. The host runner does not call this mode automatically.

Use it only after the release owner has independently identified a specific interrupted synthetic job. Pass public identifiers as instrumentation extras; no pairing secret or private key is used. A mismatch fails before any cancellation. After success, independently verify that this original website job has the cancelled terminal state, then restart the normal two-engine test explicitly.
